# 매일 Shorts 동시 제작 설계

- 날짜: 2026-10-19
- 요청: 소유자(Achii)
- 상태: 설계. 소유자는 구조를 대화에서 승인했고("응 그 구조로 가자"), 이 문서는 그 결정을 기록한다.

## 1. 왜 만드는가

소유자는 "핵심만 설명하는 shorts용 영상도 항상 같이 제작되면 좋겠다"고 했다. 목표를 묻자 "오늘의 핵심 내용 요약"이라고 답했고, 무엇이 가장 효과적인지 의견을 구했다. Shorts는 화면을 넘기는 피드라서 1~2초 안에 계속 볼지가 정해지고, 끝까지 보거나 다시 보는 비율이 추천에 크게 작용한다. 그래서 요약을 나열하는 대신 **첫 2초 훅 + 핵심 3개 + 본편 유도** 구조로 정했다. 소유자가 이를 승인했다.

## 2. 목표 / 비목표 / 실패 기준

목표
- 아침·마감 본편마다 세로(9:16) Shorts 한 편을 만든다. 하루 두 편이다.
- 40~50초 길이로 다음 구조를 따른다.
  1. 0~2초: 오늘의 숫자나 질문 한 줄을 큰 글씨로 보여 주면서 바로 말한다. 본편 제목·썸네일 훅과 같은 메시지다.
  2. 2~40초: 핵심 3개. 하나당 10초 남짓으로, 큰 숫자 하나와 해석 한 줄이다.
  3. 40~50초: "왜 그런지, 내일 볼 신호는 본편에서" 한 줄.
- 본편과 같은 브리핑, 같은 사실, 같은 목소리(eleven_v4, Vincent)를 쓴다.
- 완성 파일(세로 MP4, 업로드 문안)을 본편과 같은 brief 스레드로 보낸다. 업로드는 소유자가 직접 하고, Studio의 '관련 동영상'으로 본편을 연결한다.

비목표
- 시작·마무리 고정 멘트는 넣지 않는다. 첫 1초 인사는 이탈을 키운다. 로고는 작게 계속 보인다.
- YouTube 자동 업로드는 하지 않는다. 본편과 같이 꺼져 있다.
- 본편 대본·검토·렌더 규칙은 바꾸지 않는다.

실패로 보는 경우
- Shorts 때문에 본편 전달이 늦어지는 것. **본편이 먼저**다.
- 브리핑에 없는 숫자·사실, 매수·매도 권유, AI·도구 언급이 들어가는 것
- 세로 화면에서 글자가 YouTube Shorts UI(하단 제목·오른쪽 버튼)에 가려지는 것
- 실패한 Shorts가 무한 재시도로 크레딧이나 구독 한도를 쓰는 것

## 3. 결정된 내용

- 구조와 길이: 위 목표의 3단 구조, 40~50초. 본편의 4~5분 제한과 별개다.
- 고정 멘트 없음, 작은 로고 워터마크
- 사실 근거: 그 회차 본편의 검토를 통과한 대본과 브리핑 본문만 쓴다. 본편 대본 검토와 같은 종류의 결정적 검사를 거친다(숫자 근거, 권유 표현, 도구 언급, 금지 표현).
- 우선순위: 본편 전달이 끝난 뒤(또는 본편 렌더가 끝난 뒤) Shorts를 만든다. Shorts 단계의 실패나 지연은 본편 상태에 영향을 주지 않는다.
- 전달
  - 본편과 같은 스레드에 별도 메시지로 보낸다. 세로 MP4, 업로드 문안(제목·설명·해시태그 `#Shorts` 포함), 자막을 담는다.
  - 업로드가 필요한 메시지이므로 소유자 태그 규칙("행동이 필요한 것만")에 따라 태그한다.
- 아침·마감 모두 만든다. 소유자가 "항상 같이"라고 했다.

## 4. 제약

- 렌더 템플릿·`motion.py`가 바뀌면 `RENDERER_DIGEST`가 바뀌어 새 렌더 이미지가 필요하다(:13 또는 그 다음). 시작·마무리 장면 PR과 같은 렌더 이미지로 묶을 수 있으면 묶는다. 병합 순서는 시작·마무리 장면 → Shorts다.
- 1920×1080이 코드 곳곳에 고정돼 있다.
  - `motion.py` 뷰포트와 최종 크기 검사, `index.html`, `engine.js`, `cards.js` 절대 픽셀, 사진 정규화, 썸네일
  - Shorts는 **별도 템플릿 디렉터리와 별도 크기 검사**로 만든다. 본편 경로의 1920×1080 검사는 그대로 둔다.
- 모델 호출
  - 새 output contract는 `ProviderRequest` Literal과 검증 분기, `claude_runner.output_schema`에 추가한다. claude-runtime 이미지는 같은 커밋에서 빌드된다.
  - 요청 ID는 `video-{job}-shorts-N` 형식이다.
  - 로그인 만료 대기(`LOGIN_STAGES`)에도 새 단계를 넣는다.
- TTS 효과 키는 본편의 `speech-{index}`와 겹치지 않게 쓴다(예: `shorts-speech-{index}`). 작업 단위 크레딧 상한에 Shorts도 포함된다. 상한을 넘으면 Shorts를 건너뛰고 본편은 그대로 둔다.
- 사진·일러스트는 16:9로 정규화돼 있다. 세로 화면에서는 가운데를 잘라 쓰거나, 사진 없이 카드형으로 만든다.
- 원격(Fargate) 렌더는 같은 `MotionRenderer` 경로를 쓴다. Shorts 렌더도 원격으로 보낼 수 있어야 한다. 실패하면 로컬 대체 렌더를 쓰는 기존 방식을 따른다.
- 테스트는 실제 PostgreSQL과 실제 Chromium/FFmpeg 렌더로 한다.

## 5. 빌더에게 맡기는 것

- Shorts 대본을 받는 시점: 본편 검토 통과 직후, 또는 본편 전달 직후. 어느 쪽이든 본편을 늦추지 않아야 한다.
- 대본 스키마
  - 장면 4~5개: hook 1, 핵심 3, 본편 유도 1
  - 장면별 narration 길이 상한과 전체 글자 수(40~50초 분량, 대략 250~330자)
  - 화면 카드 데이터 형식
- 세로 템플릿 구성
  - 1080×1920 기준으로 글자를 크게 하고, 안전 영역(위 약 220px, 아래 약 380px, 오른쪽 약 140px)을 피한다.
  - 큰 숫자 카드, 해석 한 줄, 진행 표시, 말하는 문장 캡션을 넣는다.
- Shorts 전용 짧은 검토(모델 검토 1회)를 둘지, 결정적 검사만 할지
- 업로드 문안 형식: 제목 100자 이하이며 본편 제목과 같은 훅이다. 설명란 첫 줄에 본편 안내를 쓴다.
- 실패 재시도 횟수와 포기 시 Slack에 남길 한 줄

## 6. 확인 방법

- 실제 PostgreSQL 테스트
  - Shorts 단계가 본편 상태 전이를 막지 않는다.
  - 크레딧 상한 초과 시 건너뛴다.
  - 로그인 만료 시 대기 후 이어서 진행한다.
  - 효과 키가 겹치지 않는다.
- 대본 검사: 브리핑에 없는 숫자, 권유 표현, 도구 언급을 거절한다.
- 실제 Chromium 렌더로 1080×1920 프레임을 찍어 안전 영역 침범과 글자 넘침이 없는지 확인한다.
- 기존 회차(예: 10/19 PM)의 본편 대본으로 Shorts를 시험 렌더해 길이 40~50초, 자막, 프레임을 확인한다.
