# improvements 케이스 문구와 반복 실패 정리 (2026-10-22)

소유자가 "maintainer가 Slack으로 하는 말을 보면 어떤 문제가 있어서 어떤 개선이 필요하다는 건지
알 수 없다"고 했다. 10/22에 운영 DB와 Claude 실행기 영수증을 읽기 전용으로 조회했다.

- 9/16 이후 개선 작업 92건 중 운영 반영은 9/17 문서 PR #3 하나다. 진단을 마친 작업 22건,
  중간에 멈춘 작업 66건이다. 멈춘 이유는 자료 과다 30, 근거 변동 15, 운영자 대사 필요 10,
  조사 횟수 소진 6 등이다. 개선봇 PR은 #3(병합), #16(닫힘), #150(10/14부터 초안) 세 개다.
  같은 기간 main에 병합된 PR 187개 중 개선봇 PR은 #3 하나다.
- 10/15~10/22의 새 케이스 7건은 모두 직원 교육의 Claude 독립 검토가 `uncertain`으로 끝난 기록이다.
  개선봇은 이 종류를 설계상 모델 호출 없이 '운영자 대사 필요'로 멈춘다. 10/15 이후 개선봇 모델 호출은 0건이다.
  카드에는 "독립 검토의 원 요청·runtime 영수증·원 CLI 출력 대사가 필요합니다"만 있었다.
  10/21 소유자의 "뭐가 문제라는거?"에 개선봇은 어느 직원의 무엇인지 답하지 못했다.
- 3주 동안 검토 40건 중 19건이 실패했다. 실행 기록이 남은 10/09 이후 실패 13건 중 7건은
  "disallowed tool action"이다. 종료 코드는 0이었지만, 결과를 확인하기 전에 StructuredOutput이 아닌
  도구 호출이 있어 버려졌다. 5건은 종료 코드 1(대부분 약 10초), 1건은 10/19 로그인 만료다.

수치와 원문은 [운영 조회 요약](evidence/improvements-readability-20261022/production-snapshot.json)과
[현재 게시 문구](evidence/improvements-readability-20261022/before-samples.txt)에 있다.

## 바꾼 것

1. **케이스 카드와 알림.** 모델 없이 기록만으로 만든다.
   - 카드 양식: 제목, 무슨 문제, 영향, 반복, 필요한 개선, 원인 추정(검증 전), 지금, 할 일.
   - 직원은 ID 대신 이름으로 쓴다. 내부 상태 코드는 본문에서 뺐다. 번역이 없는 멈춤 코드만 괄호로 남긴다.
   - 소유자를 호출하는 답글에는 제목, 지금, 할 일만 넣는다.
   - `목록`은 승인 대기, 진행 중, 멈춤, 끝남 개수를 먼저 보여 준다. 같은 문제는 한 줄(×N)로 묶는다.
   - `maintenance_status`도 같은 요약을 돌려준다. 그래서 개선봇의 대화 답변이 카드와 같은 내용을 말한다.
2. **반복 묶기.** 확정되지 않은 Claude 검토 실패가 열린 케이스의 마지막 발생 후 7일 안에 다시 나오면,
   그 케이스에 기록만 붙인다. 새 케이스와 새 호출은 없고 카드의 '반복' 줄만 바뀐다.
   - 붙는 검토는 기존 보류 경로와 같은 무결성 검사를 통과해야 한다. 응답이 이미 저장됐거나 동결 요청이 바뀐
     검토는 붙이지 않고, 보통 진단으로 보낸다.
   - 붙은 검토 ID와 입력 digest는 케이스 영수증의 대사 목록에 더한다.
   - 7일 넘게 없다가 다시 나오면 새 케이스를 연다. 원래 검토 기록, 점수, 재호출 금지는 그대로다.
3. **Claude 실행기.** Claude가 세션에 없는 도구를 부르면 CLI는 `No such tool available` 오류 결과로 거절하고,
   실행되는 것은 없다. 이런 경우에는 결과를 버리지 않는다. 받아들이는 조건은 두 가지다.
   - 세션 초기화 기록의 도구 목록이 StructuredOutput뿐이다.
   - 그 호출에 CLI의 거절 결과가 붙어 있다.

   거절된 도구 이름은 `usage.refused_tool_attempts`에 남긴다. 다음 경우는 지금처럼 `uncertain`이다.
   - 도구 목록이 없거나 다른 도구가 있는 경우
   - 거절 문구가 없는 오류 결과(실제로 실행된 도구의 실패일 수 있다)
   - 다른 모델
   - 거절 뒤 실행이 실패한 경우

   확정되지 않은 실행의 비공개 영수증에는 종료 코드, 결과 종류, 오류 코드만 남긴다. 모델 출력 문장은 남기지 않는다.

4. **GitHub에서 닫히거나 병합된 개선봇 PR.** 지금까지 개선봇은 PR을 연 뒤 GitHub 상태를 다시 확인하지 않았다.
   그래서 닫힌 PR도 카드에서 계속 승인을 요청했다. 이제 개선봇이 이미 주기적으로 읽는 최근 PR 목록에서
   닫힌 PR을 찾아 케이스를 '닫힘' 또는 '병합됨'으로 바꾼다. 승인 기록이 이미 있는 PR은 승인 경로가 처리하므로 건드리지 않는다.
   이 확인은 Slack 승인과 같은 잠금으로 순서를 지킨다.

## 확인 범위

- 로컬 Claude CLI 2.1.308(haiku)로 재현했다.
  - 턴 제한 3: 세션에 없는 TodoWrite 호출은 `No such tool available` 오류 결과로 돌아왔다.
    이어서 StructuredOutput이 성공했다. 종료 코드는 0, `permission_denials`는 비어 있었다.
  - 턴 제한 1: 거절된 호출이 턴을 다 써서 `error_max_turns`, 종료 코드 1로 끝났다. 새 코드에서도 `uncertain`이다.
  - 운영과 같은 턴 제한 2: 네 번 모두 모델이 바로 StructuredOutput을 불렀다. 운영의 2턴 거절 흐름은 재현하지 못했다.
  - 기록: [CLI 재현 기록](evidence/improvements-readability-20261022/claude-cli-refused-tool.json).
  - 운영은 2.1.280과 opus를 쓴다. 운영 영수증에는 원 출력이 없어서 운영에서 부른 도구 이름은 확인할 수 없다.
    이번 변경 후에는 영수증에 남는다.
  - 2.1.280이 거절을 다르게 표시하면 지금처럼 `uncertain`으로 남는다. 그 경우 다음 실패 영수증의 도구 이름으로 확인한다.
- 실제 PostgreSQL 시험: 새 시험 28건(매개변수 포함)과 문구가 바뀐 기존 시험을 포함한다. Slack과 GitHub는 모의다.
  독립 코드 리뷰에서 나온 지적을 반영했다.
  - 묶기 무결성 검사
  - 거절 문구 확인
  - 대기 이유와 되돌린 반영 표시
  - 호출 답글의 필요한 개선
  - 목록에서 할 일이 다른 케이스 분리
  - 가장 최근 발생 기준 문구
- 운영 데이터 렌더링: 케이스 21건과 옛 요청 4건을 읽기 전용으로 내려받아 로컬 DB에 넣고 새 코드로 그렸다.
  모두 오류 없이 그려졌다([새 문구 미리보기](evidence/improvements-readability-20261022/after-preview.txt)).
- 배포와 실제 Slack 게시는 아직 하지 않았다. main 병합 뒤 `release.py` 자동 배포가 반영하면,
  기존 21개 카드는 다음 보고 주기에 새 문구로 한 번씩 수정된다. 수정은 호출 없이 이뤄진다.
  이미 보낸 소유자 호출 답글과 옛 요청 알림은 알림 ID가 그대로라 다시 보내지 않는다.
