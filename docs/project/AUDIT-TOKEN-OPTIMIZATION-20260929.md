# 서버 Codex 감사 토큰 최적화 — 2026-09-29

사용자 승인: “그래 최적화해줘”. 운영 worker와 Codex 런타임에 적용했고,
공용 코드는 [PR 89](https://github.com/JJongAchii/quant-ai-company/pull/89)로 main에 통합했다.

## 적용 내용

- 같은 감사의 `fail`·`unverified` 판정, 실행/형식 오류 뒤 자동 재시도를 중단한다. 원문과 영수증을 보존하고 보완 또는 명시적 대사를 기다린다.
- 서버가 자료를 최대 48,000 JSON 글자 안의 묶음으로 전달한다. 성공한 요청 안에 실제 바이트가 있고, 그 묶음의 digest에 연결된 검토 응답이 있어야 읽음으로 인정한다.
- 감사 시도마다 명시적 Codex 세션 하나를 사용한다. 완료된 직전 요청, 계정·리비전, 모델·추론 강도가 일치해야 이어받는다. 불확실한 실행을 다시 과금하지 않는다.
- 누적 검토 메모를 저장하고 최종 판정에는 핵심 인과 코드와 보충 증거를 다시 제공한다. 필수 증거가 입력 한도를 넘으면 조용히 버리지 않고 대기한다.
- 감사 한도는 64회, 비캐시 입력 750,000토큰, 출력 100,000토큰이다. 호출 사이에 검사하므로 토큰 한도는 마지막 한 호출만큼 초과할 수 있다.
- CLI의 세션 누계 사용량은 호출별 증가분으로 저장하고, 원래 누계도 영수증에 남긴다. 일반 요청의 기존 전송 형식과 digest는 유지한다.
- 모델은 **GPT-6 Astra / max**이다. 독립 감사 기준과 투자·발행 승인 조건은 유지한다.

## 확인한 절감과 한계

기존 감사 29번째 시도의 실제 자료를 PostgreSQL과 새 전달 코드에 재현했다.
이 재현의 모델 응답은 합성이며, 새로운 연구 판정이나 모델 추론은 수행하지 않았다.

| 항목 | 기존 기록 | 새 전달 방식 재현 |
|---|---:|---:|
| 필요한 모델 호출 | 123 | 32 |
| 새로 제출하는 프롬프트 글자 합계 | 9,965,638 | 1,732,155 |
| 모델 입력에 전달되지 않은 조회 조각 | 95 | 0 |

35개 파일, 1,154,771글자의 해시와 연속 범위 검사가 통과했다.
호출 수는 약 **74% 감소**한다. 글자 수는 재개된 대화 이력을 제외한 새 입력이며,
청구 입력 토큰이나 구독 한도 절감률로 해석할 수 없다.
[재현 영수증](evidence/audit-efficiency-replay.json)

공식 ChatGPT 인증으로 실제 Astra max 요청 두 개를 실행했다. 같은 thread ID를 유지했고,
두 번째 요청에 다시 적지 않은 표식을 기억했다. 두 번째 호출의 실제 입력은
11,026토큰, 캐시 입력은 9,600토큰(약 87%), 출력은 36토큰이었다.
CLI 원시 값이 누계라는 점은 세션 로그의 `last_token_usage`와 대조했다.
이는 작은 전송 시험이며, 전체 감사의 실제 절감률이나 판정 품질을 입증하지 않는다.

## 운영 상태

- Codex 런타임 코드/이미지: `d790b2ecf203b63a76425b8b2703c9d10250ff44`
- worker/배포 설정: `5fcd4353b8adab3e3fb6f11fda3f08fef7aea801`
- 최종 대조에서 기본 검증 지침을 새 자료 묶음에도 포함하도록 보완했다. 지침과 최대 길이 누적 메모를 포함한 가장 큰 프롬프트는 88,521글자로 90,000글자 한도 안이다.
- 공용 main 통합: `d742b2dea4e1e90ed040708dcc6d5ca4447d90ee`
- 당시 운영 중이던 연구 프로그램, 부분 출처 읽기 수정과 계정 라우팅 수정(`2d2ee42`)을 보존했다.
- 실행 슬롯이 비워진 뒤 worker와 Codex 런타임만 교체했다. 나머지 컨테이너 ID·이미지가 유지됐고 Codex 상태가 healthy임을 확인했다.
- `PINNED_COMPANY_WORKER_IMAGE`와 `PINNED_CODEX_RUNTIME_IMAGE`에 호환 버전을 고정했다. 이후 호환성 변경 시 두 pin을 함께 검토·갱신한다. `current`는 위 배포 설정을 가리키며 다른 서비스의 `RELEASE_COMMIT`은 바꾸지 않았다.
- 문제 감사 `e6d49c02-b55f-57ff-833d-ba5b4fcfecfe`는 37번째 시도에서 보완 대기한다. 09:22 KST 중단 뒤 새 요청 **0건**을 확인했다. 기존 미해결 증거를 보완하기 전 자동 재개하지 않는다.
- 새 테이블은 추가형 마이그레이션이다. 기존 읽기·판정·요청 영수증을 삭제하거나 덮어쓰지 않았다.

## 검증

실제 PostgreSQL·Temporal, 고정 qlab, 실제 Codex 0.154.0 설정 검사를 사용했다.
전체 검사에서 1,335개가 통과했고, 별개의 주택 알림 테스트 시각 불일치 한 건은
운영 브랜치/main에 있던 수정을 보존한 뒤 관련 검사에서 통과했다.
이후 통합 영향 범위 147개, 사용량·런타임 76개, 배포·호스트 56개, 검증 지침 포함 전달 검사 5개가 각각 통과했다.
겹치는 검사 수를 합산하지 않았다. PR 89의 최종 CI와 lint도 통과했다.
Slack은 합성 검증이며 이 작업에서 별도 Slack 메시지를 발송하지 않았다.

## 재개와 복구

실패한 packet 감사에는 일반 task retry를 적용하지 않는다. 실제 provider 영수증을 대사하고,
완료된 동일 요청의 결과를 보존하거나, 근거 보완 후 새로 고정한 감사 범위를 준비해야 한다.
`fail`·`unverified`를 같은 자료로 반복 호출해 `pass`가 나올 때까지 시도하지 않는다.
배포 영수증은 이전 이미지와 `current`를 보존한다. 롤백할 때에도 감사 대기와 불확실한
과금 기록을 유지하고, 동결된 요청 ID를 새 ID로 바꾸어 자동 실행하지 않는다.
