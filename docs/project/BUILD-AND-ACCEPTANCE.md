## 1. 첫 완성 단위

첫 번째 산출물은 실제 Slack에서 **총괄·금융전략·퀀트연구·데이터 네 BOT이 함께 일하는 상시 사무실**이다.
사용자가 휴대폰으로 요청하면 직원들이 직접 협의하고, 자료·도구 결과를 공유하며, 중간 지시를 반영한다.
맥북은 꺼져 있어도 되고, 서버 프로세스를 재시작해도 진행 중인 업무와 기억이 복구되어야 한다.

첫 흐름은 다음과 같다.

```text
휴대폰 Slack에서 연구 아이디어 전달
  → 총괄이 프로젝트와 담당자 지정
  → 금융전략과 연구 담당자가 직접 협의
  → 연구 담당자가 데이터 직원에게 자료·가용성 확인 요청
  → 실제 조회 또는 작은 결정론적 도구 실행과 증거 저장
  → 사용자가 같은 스레드에서 범위 수정
  → 새 지시에 맞춰 결과와 다음 작업 정리
  → 진행 도중 프로세스를 강제 종료하고도 같은 작업으로 재개
```

인수용 자료는 명시적인 공개·비밀 없는 작은 fixture 또는 승인된 읽기 전용 자료로 정한다.
무거운 백테스트 없이도 회사의 직접 협업·지속성·중간 개입은 검증할 수 있다.
계산 mock을 사용한 테스트와 실제 Slack·LLM·저장소를 통과한 인수 결과를 구별한다.

## 2. 구현 경계

장기 운영 코드는 개인 연구 전략 코드와 분리된 `quant-company` 서비스 경계로 둔다.
첫 패키지는 격리 qws의 `services/quant-company`에 구현했다. 아래 구조는 전체 확장의 논리 경계이며, 현재 Python 모듈 구조는 서비스 README에 기록한다.

```text
quant-company/
  app/api/                  Slack ingress, company API
  app/slack/                identity registry, threads, outbox delivery
  app/domain/               agents, projects, tasks, revisions, commitments
  app/workflows/            task workflow, agent dispatch, timers, recovery
  app/activities/           model call, tools, artifact store, compute adapter
  app/providers/            OpenAI, Anthropic adapters
  app/knowledge/            retrieval, evidence, temporal filters, memory review
  app/policy/               identities, permissions, budgets, model routes
  migrations/               PostgreSQL schemas
  agents/                   role definitions, tool allowlists, model policies
  evals/                    role tests, collaboration cases, model comparisons
  tests/                    contract, integration, crash and retry tests
  deploy/                   cloud configuration, secrets references, backup
  docs/                     operating instructions and decisions
```

### 최소 데이터 모델

| 엔터티 | 핵심 필드·불변식 |
|---|---|
| Agent | 영속 ID, 직무·모델·도구 버전, Slack 계정, 상태 |
| Project / Mandate | 시장·주기, 목표, owner, 범위·예산·현재 지시 revision |
| Message / Delivery | 원본 메시지와 수신자별 전달 상태 분리, ingress/echo 중복 제거 |
| Task / Delegation | 단일 owner, 요청·수락·산출물·기한, 의존 작업 |
| Commitment | 후속 약속의 시각·발동 조건·담당자 |
| Attempt / ToolReceipt | 모델·프롬프트·입력·도구 결과·비용·실행 호스트 |
| Artifact / Evidence | URI·digest·작성자·시점·권한·연결된 주장 |
| Memory / Claim | 상태·출처·적용 범위·가용 시점·수정 관계 |
| BudgetReservation | 회사→프로젝트→작업 배분, 동시 호출의 예약·정산 |
| Approval / Decision | 실제 사용자·대상·범위·revision·결정 근거 |

업무 생성·메시지·outbox는 같은 transaction에서 기록한다. 외부 호출은 transaction 안에서 기다리지 않는다.
저장된 command를 dispatcher가 Temporal에 전달한다. dispatcher 재시작으로 동일 command가 재전송되어도
동일 workflow/command key로 중복을 제거한다.

도구의 `operation_id`는 같은 의도에 대한 재시도 사이에 유지하고, 새 의도에는 새 ID를 발급한다.
`attempt_id`는 비용·실패를 추적하는 단위이며 외부 효과의 중복 제거 키로 대신 쓰지 않는다.

## 3. 구현 단계

### 첫 구현 묶음의 진행 순서

회사 핵심·Codex 실행기·Slack HTTP/Socket 수신·발신 outbox·배포 파일을 구현했다. 실제 PostgreSQL·로컬 Temporal 및 실제 Codex 검사는 수행했고, Slack workspace·원격 서버 인수는 연결 후 이어간다.

1. **실행 어댑터 확인:** 기존 Codex 구독으로 작은 작업의 시작·결과 수신·재개·한도 오류 처리를 확인한다.
   먼저 격리된 개발 환경에서 검증하고, 배포할 서버에서도 공식 로그인·인증 유지 경로를 검증한다.
2. **회사 핵심 구현:** 직원·프로젝트·업무·메시지·지시 revision·산출물을 저장하고, 동료 요청과 후속 업무가
   재시작 후에도 이어지게 한다. 로컬 가짜 제공자 검증과 실제 Codex 실행 증거를 구별한다.
3. **네 BOT의 실제 Slack 연결:** 총괄·금융전략·연구·데이터의 직원별 앱 manifest, 단일 서버 배포 설정,
   백업·복원 절차를 준비한다. 대상 계정·workspace·실제 비용 범위를 정한 뒤 외부 연결을 수행한다.
4. **첫 인수:** 휴대폰 요청→직원 간 직접 협업→출처 있는 산출물→사용자의 중간 수정까지 실행한다.
   맥북 종료·프로세스 재시작·중복 이벤트·구독 한도 대기·외부 백업 복원을 확인한다.
5. **직원 전문성과 연구 연결:** 아래 B·C로 세 연구팀과 공통 전문 직무를 확장하고, 승인된 첫 연구의
   데이터→3070 계산→독립 검증→보고까지 연결한다. 초기 운영에서 응답 지연·구독 사용량·비용을 실측한다.

첫 구현의 산출물은 실행 가능한 서비스, 직원 정의 4개, DB migration, Slack 앱 manifest,
서버 배포·백업 설정, 실행 증거와 운영 안내다. 외부 자격 증명은 배포 환경에 주입한다.

### A. 상시 사무실과 직접 협업

- 신규 클라우드 수신 서비스, DB, Temporal, 발신 outbox.
- 네 개의 Slack BOT 계정과 사용자 신원·프로젝트 접근 범위.
- DM·멘션·스레드·직원 간 직접 메시지와 작업 위임.
- Codex 구독 실행 어댑터, 하나의 실제 작은 도구, 산출물 저장.
- 지시 revision, 중단·재개, 비용 예약, 프로세스 장애 복구.
- A01~A12 인수. 실제 Slack과 모델 호출을 포함하는 증거를 남긴다.

### B. 세 연구팀과 전문 직원

- 국내 일·월, 글로벌 일·월, 가상자산 중빈도·고빈도·일 연구팀 등록.
- 각 팀의 독립 연구 담당자와 전문 기억·예산·프로젝트 큐.
- 공유 금융전략·데이터·개발·독립검증·리스크·운영 직무 구성.
- 최종 기본 로스터는 총괄 1 + 금융전략 1 + 연구 담당 3 + 공통 전문 직원 5 = 10명.
- 금융 지식·도구 구축, 역할별 평가, 근거와 반례의 검색.
- A13~A18 인수. 첫 기술 시연 네 BOT만으로 전체 조직 구축 완료를 주장하지 않는다.

### C. 연구 실행과 기존 자산 연결

- 시장별 데이터 계약·시점·권한·커버리지 확인.
- 기존 quant-lab 실행·검증 도구를 명시적 입력/출력 어댑터로 연결.
- 3070 제출·상태·취소·결과 회수·중복 제출 대사.
- 읽기 전용 클라우드 검증 환경과 기존 감사 규약 이관.
- 시장·주기별 실제 연구 한 건의 데이터→계산→근거→보고 경로 확인.
- 가상자산 고빈도는 별도 이벤트 데이터·시뮬레이터·실행 환경 준비 상태를 확인.
- A19~A22 인수. 실제 전략 탐색·확증은 해당 연구 범위와 예산을 정한 후 실행한다.

### D. 상시 운영의 신뢰성

비용을 줄이는 [단일 VPS 시작안](MINIMUM-SERVER.md)은 A23 자동 장애 인계를 확장 목표로 남긴다.
A24 외부 백업 복원 검증은 첫 운영에도 포함한다. 단일 서버 배포를 전체 고가용성 인수 완료로 보고하지 않는다.

- 서비스 이중화·DB 백업·복원·비밀 관리·운영 알림.
- 장시간 실행, 모델 장애, Slack 장애, worker 단절 훈련.
- 역할·모델 변경의 제한 적용·평가·롤백.
- A23~A25 인수와 운영 비용 실측.

실제 주문 실행·자본 배치는 별도 단계다. 연구 조직의 상시 운영 인수를 실제 매매 운영 인수로 대신하지 않는다.

## 5. 증거와 운영 지표

각 인수 실행은 commit·배포 버전·설정 digest·시간·환경·사용 모델·비용·입력 이벤트·관측 결과·trace 참조를 남긴다.
실제 Slack 메시지와 내부 `task_id`·`message_id`를 연결하고, 실행하지 않은 항목은 `not_run`으로 기록한다.
API key와 민감한 원문을 인수 증거에 복사하지 않는다.

### 사용자 경험

- 수신 확인 지연과 첫 의미 있는 응답 지연을 구별한다.
- Slack 이벤트 확인은 공식 3초 요구를 따른다. 모델의 실제 답변 시간은 별도로 측정한다.
- 사용자 지시가 관련 직원에게 도달하고 다음 행동에 적용될 때까지의 지연을 측정한다.
- 각 작업의 담당자, 마지막 진전, 대기 사유, 다음 행동, 사용 비용을 조회할 수 있어야 한다.

### 조직의 생산성

- 전문 분야 정답·근거 정확도, 독립 재실행 성공률.
- 사용자 개입 횟수, 잘못된 위임·누락된 후속 약속, 불필요한 왕복 메시지.
- 검증된 산출물당 모델·도구·계산 비용과 소요 시간.
- 데이터·모델·인프라·과학적 가설 실패를 구별한 기록.
- 연구에서 기각된 가설도 근거 있는 결과로 평가. 백테스트 숫자만 직원 보상의 중심에 놓지 않음.

“공개 시스템보다 낫다”는 비교는 고정된 동일 과제에서 단일 에이전트, 공개 도구의 기본 구성,
우리 구성을 같은 자료·모델 예산·판정 기준으로 평가한 뒤에만 할 수 있다.

## 6. 배포 시 정할 운영 값

설계는 특정 계정·비밀 없이 검토할 수 있다. 실제 연결에는 다음 값이 필요하다.

| 운영 값 | 필요한 이유 | 현재 상태 |
|---|---|---|
| Slack workspace와 앱 설치 권한 | 직원별 계정·채널·이벤트 연결 | 새 전용 workspace를 만들 예정. 네 앱 manifest 준비 |
| Codex 구독의 원격 공식 로그인·사용 가능 모델 | 실제 직원 실행 | 로컬 구독 모델 응답·캐시 재사용 확인. 서버의 device login은 미실행 |
| 클라우드 계정·지역·연결 | 맥북과 독립된 회사 서비스 | 기존 default 계정·서울 확인. 도메인 없는 Socket Mode 채택 |
| 월 비용 상한·동시 작업 수 | 서버 규모와 구독 사용량 정책 | AWS 구성 월 6~8만원 계획 예산·동시 Codex 1개. 실제 구매 전 생성 계획 검토 |
| 금융 자료 사용 권한·데이터 구독 | 전문 지식과 시장별 데이터 | 기존 자산과 새 필요분을 구분해 조사 |
| 허용된 예약 업무·사용자 알림 시간 | 주도적 후속 업무와 불필요한 알림 조절 | 배포 설정으로 구체화 |

위 값이 없는 동안에도 로컬 모듈·fake provider·테스트 환경의 구현은 가능하다.
실제 유료 자원 생성·외부 앱 설치·업무 발신은 해당 대상과 비용 범위가 정해진 배포 단계에서 수행한다.

## 7. 현재 산출물의 검증 범위

구현·검증 증거와 정확한 실행 환경은 `IMPLEMENTATION-VALIDATION.json`에 남긴다.
실제 Slack 메시지 발신·클라우드 생성·연구 실험·거래는 수행하지 않았다. 전체 조직 구축의 완료 판정은 위 운영 인수 결과가 생긴 뒤에 한다.
