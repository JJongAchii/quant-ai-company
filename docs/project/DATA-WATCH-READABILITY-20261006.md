# data-watch 업데이트 현황 가독성

이전 일일 알림은 한 메시지에 내부 데이터셋 이름, 중복 날짜, 파일 교체일과 긴
점검 설명을 함께 표시했다. 사용자가 최신 데이터 날짜와 필요한 조치를 빠르게
읽지 못했으므로 사람이 읽는 이름과 짧은 문장으로 다시 구성했다.

일일 알림은 수집·반영 경로 점검, 갱신 일정 확인, 읽기·날짜 확인 문제를 먼저
보여 준다. 각 항목은 마지막 데이터 날짜와 빠진 공개 자료 또는 다음 확인을
한 줄로 연결한다. 한국시장 자료와 SEC 재무 자료 등 관련 항목은 날짜·상태·오류가
같을 때만 묶으며, 다른 날짜나 오류가 있는 구성원은 각각 표시한다. 나머지 주요 자료의
마지막 날짜는 아래에 모아서 보여 준다. 월별 OECD 자료는 날짜 대신 기준월을
표시한다. 빈 고정 연구 입력 안내와 파일 검사 성공 개수는 일일 알림에서 뺐다.
등록된 연구 입력이 존재하면 검사 현황과 오류는 계속 표시한다.

`목록`은 38개 데이터셋을 한국 시장, 미국 시장, 경제지표, 한국 공시, 미국 공시·펀드,
고정·이력 자료로 묶는다. 각 줄에는 한글 이름, 데이터 날짜, 파일 교체일이 있다.
내부 키와 상세 검사 영수증은 기존 운영 API에 남아 있다. 표시 날짜는 전체
데이터셋의 최대 날짜이며 종목별·시리즈별 완전성을 보증하지 않는다.

- 🔴 공개 자료 미반영 또는 등록된 수집 기준 지연: 수집·반영 경로 점검.
- 🟠 오래 같은 날짜인 자료: 휴장·공표 주기와 수집 일정을 확인할 항목.
- ⚪ 파일 정보나 날짜 읽기 실패: 검사 도구 또는 날짜 항목 점검.

날짜 선택, 최신성 기준과 기존 공개 자료 비교 기준은 바꾸지 않았다. 조회 실패
시에는 이전 성공 기록의 날짜임을 명시한다. 복구 답글은 회복한 검사 결과를
설명하며 이전 실패의 영향 문장을 반복하지 않는다.

기본 알림 형식으로 선택했다.

## 운영 적용과 검증

10/06 10:36 KST에 640자 새 일일 요약이 실제 `#data-watch`에 발송됐다.
DB outbox의 `delivered` 메시지 `8229fb0c-b9e2-56cd-b1a4-85f3b6e6b7e6`과 Slack
읽기 결과의 `client_msg_id`, 발송 시각 `1791250578.956599`, 봇 계정이 일치했다.
Slack이 이모지를 이름으로 정규화한 부분을 되돌리면 메시지 본문도 일치한다.
[운영 증거](evidence/data-watch-readability-20261006/live.json)에 확인 결과를 기록했다.

표시 코드 커밋 `8508954320877144e8f24cb52c8353c0e18f514a`의 파일 두 개를 각 서비스의
기존 이미지 위에 적용했다. API·Slack 수신기 기반 이미지의 소스 168개와 data-watch
작업자 기반 이미지의 소스 135개를 각각 비교해 `data_watch/coverage.py`와
`data_watch/reporting.py`만 달라짐을 확인했다. 기존 전체 소스 커밋 라벨과
`COMPANY_CODE_COMMIT`은 유지하고 표시 코드 라벨을 별도로 남겼다. 각 교체에서 실행
명령, 환경, 마운트, 리소스·보안 설정을 비교했고, 다른 서비스의 컨테이너 ID와
재시작 횟수를 보존했다. API는 healthy, 세 대상은 실행 중·재시작 0회이며
기존 릴리스 링크와 release timer도 유지됐다. 배포 잠금과 진행 중인 읽기 검사로
거절된 시도에서는 대상 컨테이너를 교체하지 않고, 조건을 다시 확인한 뒤 적용했다.

실제 PostgreSQL·Temporal과 메시지 렌더링 테스트 38건, Slack·회사 서비스·배포
계약 테스트 66건, Ruff, 소스 커밋의 CI가 통과했다. Slack 전송 단위 테스트는
모의 환경이며 실제 일일 알림의 읽기 증거와 구분한다. 운영에서 `목록` 렌더 결과는
38개 항목·1,634자였지만, 실제 소유자가 `상태`·`목록`을 입력한 왕복은 아직 검증하지
않았다. 날짜 선택과 수집 기준은 이번 표시 개선에서 바꾸지 않았다.
