# 회사 Slack 최종 구조

2026-09-22 사용자 승인. 이 회사 저장소와 piddock에서 설계·구현·통합한다.
knifefish의 논의는 참고 자료이며 다른 세션의 구현을 기다리는 의존성이 아니다.

## 사용 관점

평소에는 본사에서 회사 현황과 결정할 일을 보고, daily-brief에서 시장을 파악한다.
업무는 목적별 채널의 스레드에서 진행한다. 직원은 여러 채널에 참여할 수 있지만
채널마다 최종 답변과 후속 조치의 책임 담당자는 하나다.

목표 구조는 핵심 업무 7개, 기존 피드 3개, 소셜·테스트 2개다. 실제 리스크 검토가
준비되면 risk-desk를 추가한다. 아래 이름은 목적별 권장 이름이며 설정은 이름 대신
Slack 채널 ID에 연결한다. 이 문서만으로 채널 생성·이름 변경·예약 발송·직원 활성화가
완료된 것으로 간주하지 않는다.

| 채널 | 책임 담당 | 게시 내용과 사용 규칙 |
|---|---|---|
| company-hq | 총괄; 운영 담당은 도구 검증 후 참여 | 기존 전체 채널 활용. 평일 18시 KST 우선순위·완료·막힘·결정 대기 요약. 직접 개입이 필요한 일은 즉시 알림. 승인 대상은 원문 스레드로 연결 |
| daily-brief | Reporter, 금융전략 검토 | 정기 기능 활성화 후 매일 08:30 KST. 국내·글로벌·가상자산의 확인 가능한 시황과 당일 일정. 휴장 시장은 마지막 거래일, 가상자산은 집계 구간 표시 |
| market-deep-dive | 금융전략 | 요청형 시장·뉴스·자산 분석. 사실과 해석, 반론, 출처와 기준 시각을 구분. 연구 실행은 별도 승인된 요청으로 연결 |
| research-center | 총괄 | 연구 질문·가설·승인된 실험·반론·독립 검증. 연구 건별 스레드에서 진행 |
| research-library | 총괄; 연구·검증 담당 자료 제공 | 채택·기각·보류와 근거, 보고서, 검증 범위, 실패 원인, 재검토 조건. 확정 결과 게시; Slack은 회사 저장소의 증거를 링크 |
| data-watch | 데이터 | 전체 레이크 개요와 핵심 데이터 상세 검사. 데이터 사용 가능성·장애 영향·복구 상태 표시 |
| improvements | Maintainer | 명시적 요청과 관측된 실패의 케이스별 접수·진단·수정·검증·PR·승인·반영 상태 |
| hot-news | Reporter | 중요한 새 사건과 사실을 원문 근거와 함께 전달 |
| quant-feeds | 리서치 자료 수집 담당 | 논문·방법론·데이터 등 연구 재료. 피드 등록을 실험 승인으로 해석하지 않음 |
| tech-feeds | Tech Scout | AI·개발·인프라 등 기술 개선 재료. 피드 등록을 코드 수정 승인으로 해석하지 않음 |
| 소셜 | 사용자와 참여 직원 | 비업무 대화 |
| test | 운영·개발 담당 | 합성 데이터와 명시된 인수 검사. 실제 운영 성과로 보고하지 않음 |
| risk-desk (후속) | 리스크 | 검증된 전략 후보 또는 승인된 포트폴리오 입력·계산 도구가 준비된 뒤 노출·집중·상관·유동성·손실 시나리오 검토 |

company-ops의 목적은 company-hq에 통합한다. research-review의 목적은 연구 스레드의
독립 검증 절차와 research-library의 판단 기록에 반영한다. 직원·시장별로 별도 채널을
늘리지 않는다. 독립 검증은 별도 권한과 실제 검증 증거로 보장한다.

## 공통 동작

- 한 업무의 기준 스레드는 하나다. 다른 채널은 요약과 링크만 제공한다. 본사의 짧은
  답변을 다른 스레드의 PR·연구 승인으로 적용하지 않는다.
- 본사 요약은 실제 기록의 담당·단계·대기 이유·다음 조치·원문 링크를 제공한다.
  직원 활성 여부, 도구 사용 가능 여부, 평가 결과, 워커 건강 상태를 구분한다.
- 사용자 멘션은 결정·추가 정보·직접 개입에 사용하고 일반 진행은 조용히 게시한다.
- 모델은 typed proposal을 제출한다. 서버가 소유자·채널·revision·한도를 검증한 뒤
  적용한다. 단순 상태 조회·예약·중복 판정·전달은 모델을 호출하지 않는다.
- PostgreSQL이 업무·케이스·점검 기록을, Temporal이 실행·재시도·예약을 소유한다.
  Slack 전달 영수증을 보존하고 불명확한 쓰기를 자동 재실행하지 않는다.

## data-watch: 다음 구현 범위

사용자가 선택한 **전체 개요 + 핵심 상세**를 따른다. 전체 카탈로그와 객체 메타데이터를
30분마다 확인하고 신규·변경 객체에만 기존 제한된 descriptor 조회를 수행한다.
회사 서버에서 전체 레이크를 읽거나 qdata의 전량 coverage 함수를 실행하지 않는다.

초기 상세 대상은 승인된 국내 ETF 연구 입력 버전이다. 기존 워커의 읽기 전용 검사 결과를
입력 버전·범위와 대조해 소비한다. 새로운 연구·학습이나 상류 수집 저장소 수정은 포함하지 않는다.

업로드 시각, 실제 데이터 기준일, 검사 시각을 구분한다. 데이터별 거래 달력·갱신 주기 계약이
없으면 `기준 미등록`, 검사하지 못한 범위는 `미검사`로 표시한다. 소량 표본과 전체 입력 검사를
구분하고 최신 레이크의 장애가 과거 고정 연구 입력에도 영향을 주는지 따로 판단한다.

매일 09시 KST 요약과 상태 변화 알림을 게시한다. 같은 장애는 한 케이스로 모으고 영향받는
데이터·연구, 마지막 정상 상태, 다음 점검 시점을 표시한다. 복구는 재검사 증거로 확인한다.
수리가 필요하면 improvements와 연결하며, 연구 입력을 자동 교체하지 않는다.

## 구현 순서와 활성화

1. **이번 구현:** improvements 전용 Maintainer, 케이스 스레드·상태 카드·독립 보고와 승인 연결.
   [사용·설치 절차](../improvements.md), [검증 결과](IMPROVEMENTS-VALIDATION.md)를 따른다.
2. **다음 구현:** 위 data-watch 범위를 구현한다.
3. company-hq 운영 요약과 market-deep-dive 요청형 분석.
4. research-library와 정기 daily-brief. 다른 작업트리에서 병행 중인 기능은 실제 합쳐진
   커밋과 인수 증거를 확인해 재사용하며, 이 문서가 그 작업의 완료를 뜻하지 않는다.
5. 첫 자율 연구 인수 이후 글로벌·가상자산 담당을 각각의 데이터·도구 검증에 맞춰 활성화한다.
   운영·검증·리스크 담당도 업무별 준비 조건을 충족한 뒤 활성화한다. 일괄 활성화하지 않는다.

모든 설계·운영 증거는 회사 저장소에 남긴다. 새 유료 구독·서버·모델 교체를 기본 전제로 삼지 않는다.
