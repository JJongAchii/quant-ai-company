# 운영 상태 질의·운영 알림 (2026-10-14)

운영 방법은 [ops-watch.md](../ops-watch.md)에 있다. 이 문서는 왜 만들었는지와 검증 범위를 기록한다.

## 요청

오너는 다음 세 가지를 요청했다.
1. Slack에서 서버 작업 진행 상황을 물으면 실제 서버 상태로 답할 것
2. 문제가 생기면 경고하고 계속 감시할 것
3. 배포할 때 서버 전체가 멈추는지 확인하고 개선할 것

오너가 정한 방식은 세 가지다.
- 브리핑 스레드에 답글로 묻는다
- 경고는 새 운영 채널로 받는다
- 봇은 읽기 전용 도구로만 상태를 본다

## 운영에서 확인한 사실 (읽기 전용 조회, 09:30 KST 전후)

- **브리핑 스레드 답글이 무시됐다.**
  - 원인: slack-socket 컨테이너의 `SLACK_ALLOWED_CHANNELS`에 브리핑 채널이 없어서 `SlackIngress.accept`가 답글을 무시했다. 10/14 아침 브리핑 스레드 질문은 `inbound`에 기록이 없다.
  - 조치: sargassum 세션이 11:3x KST에 slack-socket·account-gateway·worker의 값을 api와 같은 10개 채널로 맞췄다. 이미지는 바꾸지 않았다.
  - 남은 불일치: 아래 미리보기에서 서비스 4개의 값이 아직 다르다.
- **배포 때 서버 전체가 멈췄다.**
  - 09:27 KST에 api/worker만 바꾸는 apply 스크립트가 실행됐다.
  - 스크립트는 postgres를 뺀 모든 컨테이너를 `docker stop`하고, 백업한 뒤 다시 켰다.
  - 같은 정지가 `deploy/state_backup.py`의 일관성 백업과 매일 03:10 KST 백업에도 들어 있다.
  - 동시에 재기동되면서 시작 단계의 스키마 DDL이 다른 쿼리와 잠금 교착을 일으켰다. dispatch는 1회 크래시 후 재시작했다(restarts=1).
  - 개선(온라인 백업, 변경 서비스만 교체, 스키마 digest 생략, SIGTERM 정상 종료)은 sargassum 세션의 릴리스 도구 설계에 넣기로 합의했다. 이 변경에는 포함하지 않는다.
- **감시 공백**: 컨테이너 종료·재시작·OOM, 디스크, 막힌 발송·작업, 백업 실패를 알리는 장치가 없었다.

## 이 변경

- 호스트 수집기 `deploy/ops_probe.py`: 1분 주기, systemd timer
- 상태 도구 `ops_status`:
  - 사용 주체: Director, 그리고 브리핑 스레드의 Analyst
  - `상태` 명령은 모델 없이 바로 답한다
- 감시 `ops/watch.py`:
  - 실행 위치: dispatcher 루프, 60초 주기
  - 알림 대상: 운영 채널
  - 동작: 상태 경고와 해소, 사건 경고는 한 번만
- 비상 경로: PostgreSQL·dispatch 정지, 또는 감시가 멈췄을 때만 Slack에 직접 알린다
- 자동 릴리스 보고(ADR 0045 §8): sargassum-cf의 요청으로 추가했다. 수집기가 `release-status.json`을 읽고, 감시가 실패·보류·지연·운영자 단계를 알린다.

## 검증

- **실제 PostgreSQL에서 테스트**: `tests/test_ops.py`
  - 상태 요약이 6KB 이하이고 digest가 없는지
  - 도구 권한
  - 경고 2회 확인과 해소
  - 치명 경고의 오너 멘션과 사건 경고의 해소 생략
  - 컨테이너 대량 중지 묶음과 배포 창
  - 유닛 실패, 비활성화 시 stale 처리
  - `상태` 즉시 응답
- **시뮬레이션**: `tests/test_ops_probe.py`
  - 환경값 digest에 원문이 남지 않는지
  - 로그 원문이 저장되지 않는지
  - 비상 경로가 한 번만 알리고 한 번만 해소하는지
  - 결과 불명 전송을 재전송하지 않는지, 거부된 전송은 재시도하는지
  - Slack 전송은 모두 MockTransport와 가짜 sender를 썼다. **실제 Slack 전송은 하지 않았다.**
- **운영 읽기 전용 미리보기** (`--print`, 10/14 11:4x KST): DB·Slack에는 쓰지 않았고 임시 파일은 바로 지웠다.

  | 항목 | 결과 |
  |---|---|
  | 소요 시간 | 1.9초 |
  | 크기 | 8KB |
  | 수집 오류 | 0 |
  | 비밀값 패턴 | 0건 |
  | 컨테이너 | 18개 모두 실행 중 |
  | dispatch | restarts=1 |
  | 디스크 여유 | 59.6GB |
  | 메모리 여유 | 5.4GB |
  | release 유닛 | `exec-condition`(가드가 건너뜀, 경고 제외) |

  - 남은 불일치: `SLACK_ALLOWED_CHANNELS`
    - 같은 값 9개: account-gateway, api, briefing-data-worker, dispatch, news-worker, slack-socket, tech-feed-worker, video-worker, worker
    - 다른 값 A: data-watch-worker, housing-feed-worker, maintenance
    - 다른 값 B: quant-feed-worker
- **main 전환 뒤 다시 본 운영 상태** (`--print`, 10/14 13:59 KST, 읽기 전용):
  - 18개 컨테이너가 모두 실행 중이다. 앱 이미지는 모두 `5454e3d`이고, 재시작은 0회다.
  - `SLACK_ALLOWED_CHANNELS`를 포함한 공용 환경값 불일치는 없다(`drift` 비어 있음). slack-socket·worker·dispatch·api 모두 브리핑 채널을 허용한다.
  - 디스크 여유는 41.6GB로 줄었다(새 릴리스 이미지 빌드). 경고 기준 20GB보다는 크다.
  - 브리핑 채널 `inbound`는 최근 2일 동안 0건이다. 허용 채널을 고친 뒤 브리핑 스레드에 사람이 답글을 단 적이 없어서, 실제 수신은 아직 확인하지 못했다.
- **릴리스 보고 읽기** (10/14 14:3x KST, `--print`): 상태 파일이 아직 없어서 `release`가 비어 있고, 수집 오류는 없다. 실제 보고 형식은 #151의 운영 보고 실행 증거(`host-report-run.json`)와 같은 필드로 테스트했다.
- **운영 배포 안 함**: 배포 동결 중이라 운영에는 설치하지 않았다. 실제 Slack 질문 답변, 운영 채널 경고, 비상 경로는 설치 뒤에 실제로 확인해야 한다.
