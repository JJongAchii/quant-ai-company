# 최근 관측 구간을 사용하는 검색 트렌드

사용자가 최근 몇 시간의 순위와 검색량 해석을 논의한 뒤 “너가 생각하는 최적으로 진행해줘”라고
승인했다. 정기는 최근 6시간, 수시 요청은 1시간 관측 우선·6시간 보충으로 구현했다.
08:00·14:00·20:00 KST 발송, 30분 전 자료 동결, 스포츠 제외, 합계 10개 목표를 유지한다.

## 순위와 해석

동결 시각을 포함하지 않는 직전 6시간의 키워드별 마지막 관측값을 사용한다.
요청에서는 마지막 관측이 직전 1시간에 속하는 후보를 먼저 배치한다. 각 그룹 안에서는
30분 이내 최신 성공 목록에 있는지, 신규 포착 또는 규모 표시 상승인지, 최근 규모 표시,
마지막 관측 시각, 제목으로 결정적으로 정렬한다. 후보는 최대 30개다.

구간 경계 직전 30분 안의 관측과 이후 30분 이하 간격의 수집이 있어야 신규·변화를 판정한다.
같은 RSS 게시 시각을 가진 검색어의 경계 이전 값과 최신 값만 비교한다. 수집 공백·부분 이력·
이전 기준 없음·급상승 회차 변경은 비교 불가다. 반복 관측을 더하거나 과거 최대값을 현재값으로
표시하지 않는다. `peak_snapshot`은 기존 미리보기 검증기의 호환 필드로 남기되 최신값의 영수증을 가리킨다.

화면에는 관측 구간·현재/이전 관측·마지막 관측 시각·신규/규모 변화가 표시된다.
확인한 주요 뉴스 보충은 번호가 없는 `함께 볼 주요 이슈 · 순위 외`에 따로 표시한다.
네이버는 최근 7일/이전 7일 상대 추이를 유지한다. 0–100 지수에서 절대 검색량을 역산하지 않는다.
Google 규모 표시도 이 서비스의 1시간·6시간 동안 발생한 검색 횟수로 해석하지 않는다.

편집 정책을 v4로 올렸다. 이전 정책의 대기 결과는 기존 정책 검사로 발송되지 않는다.
10분 캐시는 같은 정책의 수시 요청끼리만 재사용하며, 정기 6시간 편집을 요청 답변에 재사용하지 않는다.
모델 하루 12회 중 정기 6회 확보, 네이버 하루 100회, 요청 ID·불명 결과 처리·기존 큐 우선순위는 유지한다.

## 검증과 운영 반영

[검증 영수증](evidence/trend-window-20261008/qualification.json)은 실제 임시 PostgreSQL과
로컬 Temporal을 사용하는 자동 검사와 외부 HTTP·모델·Slack 모의를 구분한다.
배포 후보는 운영 중인 4개 부모 이미지의 소스를 각각 가져와 `trend_feed/ranking.py`,
`editor.py`, `store.py`만 반영했다. 다른 서비스 변경과 실제 dispatcher의 큐 수정을 보존한다.

뉴스 작업자 후보는 96개, dispatcher 후보는 98개 검사를 통과했다. API·Socket 후보는 각 29개
요청 수신·권한·중복·정책·순위·캐시 검사를 통과했다. 실제로 송신하지 않는 API/Socket의 과거
송신·CLI·모델 배정 코드는 이번 배포 범위에 포함하지 않는다. 송신 검증은 실제 dispatcher 부모에서 수행한다.

[자료 미리보기](evidence/trend-window-20261008/preview.json)는 실제 DB에서 읽은 새 관측 구간에
기존 검증 분류만 재사용했다. 처음 보는 후보는 생략했으며 생략 목록을 영수증에 기록했다.
이 단계에서 DB 쓰기·모델·Slack 호출은 0회다. 새 후보의 실제 편집·발송 검증은 별도로 기록한다.

운영 전환과 실제 발송 확인은 진행 중이다. 완료 전에는 이 문서를 배포 완료 증거로 사용하지 않는다.
