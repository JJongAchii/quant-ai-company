# data-watch 현황 메시지 해석 개선

2026-09-28 KST. 사용자는 기존 일일 요약에서 숫자는 보이지만 현재 데이터를 어떻게
판단해야 하는지 알기 어렵다고 지적했다. 특히 09:58 KST 게시물은 그 시각의 전체
목록 조회가 실패했는데도 이전에 저장한 “38개 중 37개 확인”을 먼저 보여 주었다.
운영 기록상 10:01 KST 재조회는 성공했다. 조회 실패를 데이터 손상으로 해석하거나
지난 목록을 현재 목록으로 표시해서는 안 된다.

새 요약은 먼저 현재 결론을 말한다. 목록 조회에 성공해도 최신성 기준이 모두
미등록이면 “전체 최신 여부 미판정”으로 표시한다. 파일 정보 조회 성공은 데이터 값,
종목별 누락, 최신성 검사가 아님을 바로 옆에 적는다. `us_prices`는 검사 도구의
2 MiB 파일 정보 읽기 한도에 걸린 **미확인 항목**이며, 원본 손상이나 데이터 지연
판정이 아니다. 별도 연구 고정 입력 6개는 이 메시지로 검사했다고 주장하지 않는다.
요약 말미에는 필요한 조치와 다음 자동 목록 확인 시각을 표시한다.

목록 조회가 실패하면 제목을 “현재 목록 조회 실패”로 바꾸고, 이전 성공 목록을
확인한 시각을 숫자보다 먼저 표시한다. 이전 성공 기록이 없으면 숫자를 현재 목록으로
보여 주지 않는다. 처음 조회 자체가 아직 없는 경우는 “첫 목록 조회 대기”로 구분한다.
오늘 이미 발송한 기존 형식의 요약은 삭제하거나 전송 영수증을 수정하지 않는다.
새 요약 형식 버전은 3이며 배포 후 그날의 새 요약을 별도 ID로 한 번 게시한다.

운영에 적용한 병합 코드 `958630e`에서 실제 PostgreSQL·Temporal 전체 테스트
1,173개 통과(38개 건너뜀), data-watch 집중 테스트 30개 통과, 배포 계약 31개와
Ruff 통과를 확인했다. PR #74의 서비스 CI도 통과했다.

2026-09-28 13:51 KST에 새 형식의 메시지가 `#data-watch`에 한 번 게시됐다.
제목은 “데이터 현황 · 확인 필요 1건”이고, 첫 결론은 “데이터 전체가 최신인지 아직
판단할 수 없습니다”이다. 이어서 파일 정보 38개 중 37개 확인, `us_prices` 한도
초과, 최신성 기준 미등록, 별도 연구 입력 미검사를 각각 구분한다. 386자짜리 슬랙
메시지 한 개의 ID·전송 시각·길이가 PostgreSQL 발송 영수증과 일치한다.

같은 시점의 마지막 완료 목록 조회는 13:30 KST에 성공했다. 이는 데이터가 모두
최신이거나 누락이 없다는 뜻이 아니다. 현재 등록된 데이터별 갱신 기준이 없고,
고정 연구 입력 검사는 꺼져 있다. 운영 적용은 `data-watch-worker` 컨테이너 한 개만
교체했다. 당시 병행 중인 주택 피드 릴리스 `ccdcc43`의 현재 링크·설정과 다른
서비스 컨테이너 ID를 보존했고, 자동 릴리스 타이머는 활성 상태다. 상세 영수증은
[data-watch 운영자 현황 적용 증거](evidence/data-watch-operator-live-20260928.json)에 있다.

사용자는 이 형식도 현황 파악에 부족하다고 재지적했다. “전체 최신 여부 판단 불가”와
37/38 파일 검사 수치 대신, 소스별 마지막 **데이터 날짜**, 공개·수집 예정 날짜와의 차이,
파일 교체일 및 검사 실패를 보여 주어야 한다. 따라서 위 운영 적용은 전송 검증의
역사적 기록이며 최종 메시지 인수가 아니다. 후속 설계와 실측은
[소스별 갱신 현황](DATA-WATCH-SOURCE-STATUS-20260928.md)에 기록한다.
