# Maintainer와 improvements

기존 개선 엔진에 전용 대화 신원과 영속 케이스 화면을 연결한다. 새 기능은 기본 비활성이다.
전체 채널 구성과 후속 data-watch는 [최종 설계](project/SLACK-COMPANY-DESIGN.md)를 따른다.

## 사용

- improvements에 개선 요청이나 질문을 쓰면 Maintainer가 응답한다. 멘션 없이도 동작한다.
  다른 직원 앱에 같은 Slack 이벤트가 전달돼도 총괄의 중복 업무는 만들지 않는다.
- Maintainer는 일반 질문·아이디어를 논의하고, 명시적 진단 요청에만 `maintenance_review`를
  제안한다. 접수 영수증은 진단 완료를 의미하지 않는다.
- 새 요청은 고정 케이스 ID를 가진다. 전용 채널의 새 요청은 사용자 원문 스레드에 봇 상태
  카드를 게시한다. 다른 승인된 채널의 요청은 improvements에 새 케이스 스레드를 만들고,
  실제 Slack 전달 영수증을 받은 뒤 원문에 링크를 남긴다. DM 요청은 기존 DM 경로를 유지한다.
- 상태 카드는 Maintainer 자신의 메시지만 수정한다. 사용자 원문을 수정하지 않는다.
  단계, 최근 진행 시각, 모델 요청·quota 대기, PR와 반영 상태를 실제 기록에서 표시한다.
- 같은 케이스의 후속 질문은 기록을 조회해 답한다. 명시적으로 새 진단을 요청하면 별도
  불변 요청·케이스가 생긴다. 이미 고정된 실행 입력이나 승인 대상을 대화만으로 덮어쓰지 않는다.
- 케이스 스레드의 `상태`는 해당 기록을, 채널의 `목록`·`상태`는 소유자가 볼 수 있는 최근
  20개 케이스를 모델 호출 없이 보여 준다. 목록 역시 전체 조직에 대한 인증이나 성과 점수가 아니다.
- 검증된 PR 알림이 실제 전달된 후 같은 소유자가 같은 케이스 스레드에서
  `PR 123 반영해`로 정확한 후보를 승인한다. 원래 접수 채널에서는 새 케이스의 승인을 받지 않는다.
  기존 케이스는 기존 스레드와 승인 방식 그대로 마무리한다.

## 자동 관찰과 보고

전용 채널 기능이 활성화되면 일반 대화·아이디어는 자동 진단의 시작 조건에서 제외한다.
활성화 시각 이후의 기록된 업무 오류와 객관적 직원 평가 실패만 자동 접수한다.
quota 대기, 실행 횟수 한도, 연구 워커 대기는 자동 수리할 결함으로 분류하지 않는다.
기존 관찰 기록과 개선 작업을 전용 채널로 일괄 복사하지 않는다.

현재 승인된 연구 단계가 두 시도 이상 응답 형식·계약 오류로 멈추면 별도 기술 진단으로 접수한다.
현재 소유자·버전·허용 채널과 활성 프로그램/미션을 대조하고, 완료·취소·일시정지·정상 데이터
대기는 제외한다. 같은 단계·시도는 한 번만 관찰하며 원래 연구의 판단·예산을 변경하지 않는다.
독립 설명 검토의 `invalid_review`·`uncertain`도 운영 오류로 접수한다. `uncertain`은 원 호출과
영수증을 보존한 운영자 대사 대상이다. 자동 재호출하거나 직원의 객관적 평가 실패로 기록하지 않는다.

진단 원본은 DB에 유지한다. 모델 입력에서 경로 목록이나 상세 내용이 생략되면 생략 수와 요약
표시를 남기고, 기존 코드 검색 도구로 필요한 원문을 찾을 수 있다. 이미 예약한 모델 입력은 수정하지 않는다.

`company-maintenance-v1`과 기존 모델 요청·CI 실행은 보존한다. 별도의 Temporal workflow
`company-maintenance-reporting-v1`이 `-maintenance-reporting` 큐에서 60초마다 경량 보고를 실행한다.
보고는 DB를 읽고 outbox에 기록할 뿐 모델·GitHub·Slack 네트워크를 호출하지 않는다. 별도 모델
슬롯이나 서버를 추가하지 않는다. 같은 프로세스/DB 장애 시에는 보고도 중단될 수 있다.

미확인 루트 게시에는 후속 카드 수정이나 PR 승인 알림을 보내지 않는다. 타임아웃·5xx·프로세스
중단 후 불명확한 쓰기는 `uncertain`으로 보존하고 자동 재전송하지 않는다. 상태 카드 갱신도
선행 쓰기의 결과를 확인하기 전에는 추월하지 않는다. 429는 기존 명시적 지연 정책을 따른다.
원문·대상 채널의 권한 또는 원문 revision이 바뀌면 새 게시·승인을 중단한다.

## 설치와 운영 인수

1. 검토할 코드 커밋을 고정하고 기존 PR·승인·배포 절차로 반영한다.
2. [Maintainer 앱 manifest](../slack-apps/maintainer.json)로 앱을 준비한다. Socket Mode의
   앱 토큰에는 `connections:write`를 사용한다. 실제 값은 서버의 기존 credentials 파일에
   `maintainer` 항목으로만 보관한다. 모델 컨테이너나 Git에는 전달하지 않는다.
3. improvements 채널을 준비하고 Maintainer를 초대한다. 채널 ID를 `SLACK_ALLOWED_CHANNELS`와
   `IMPROVEMENTS_CHANNEL_ID`에 넣고 `COMPANY_IMPROVEMENTS_ENABLED=true`를 설정한다.
   기존 maintenance 설정의 허용 소유자와 회사 허용 사용자가 일치해야 한다.
4. 기존 마이그레이션과 maintenance 초기화를 실행한다. api·worker·dispatch·slack-socket·maintenance가
   같은 설정과 커밋을 사용하게 한다. Maintainer의 모델/effort는 현재 engineer 설정을 재사용한다.
   다른 비활성 직원은 활성화하지 않는다.
5. 실제 Slack에서 새 요청·후속 질문·상태·중복 이벤트·케이스 링크·PR 알림·정확한 승인·반영 보고를
   확인한다. 실제 구독 모델 응답과 모의 응답을 구분하고, 긴 진단 중 보고가 계속되는지 확인한다.
6. 활성화 증거는 `docs/project/evidence`에 남긴다. 로컬 테스트나 앱 manifest 생성만으로
   앱 설치·운영 배포·실제 Slack 인수가 완료됐다고 기록하지 않는다.

되돌릴 때는 새 intake 설정을 비활성화하고 기존 케이스·outbox·Temporal 기록을 유지한다.
불명 전달·이미 승인된 반영은 해당 영수증을 검토한다. DB 삭제나 새 워크플로 ID로 재실행하지 않는다.
