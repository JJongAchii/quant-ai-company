# 개선 BOT 운영

정책: 수정·테스트·draft PR까지 자동, 운영 반영은 검토 후 진행.
[설계](adr/0013-review-controlled-maintenance.md)에 데이터 범위·예산·실패 처리·권한을 정의한다.
[행동·조직 개선 확장](adr/0014-behavior-and-organization-improvement.md)은 장기 관찰과 전후 평가를 정의한다.

## 현재 상태

구현·검증용 코드를 준비했고, GitHub App 설치와 운영 서버 maintenance profile 활성화를 확인했다.
실제 구독 기반 수정 PR 인수·추가 메모리 실측과 전체 인수 완료는 아직 확인하지 않았다. 현재 네
직원이 이 기능을 이미 사용한다고 보고해서는 안 된다. 기존 서버와 Slack 회사는 맥북 전원과
무관하게 운영 중이다.

## 검토 후 연결할 구성

1. 이 저장소에만 GitHub App을 설치한다. Contents/PR write와 Actions read만 부여한다.
   웹훅·도메인은 필요하지 않다. 비밀 key를 채팅·Git·모델에 보내지 않는다.
2. `deploy/maintenance.example.json`의 예제 App/installation ID와 허용 사용자 ID를 실제 값으로
   교체해 서버 `config/maintenance.json`에 둔다. key는 `secrets/maintenance_github_key`에 둔다.
   허용 사용자는 기존 Slack 허용 사용자 목록의 부분집합이어야 한다.
3. 검토한 정확한 서비스 커밋과 `deploy/qdata-source.json`의 qdata archive로 maintenance 이미지를
   빌드한다. 기본 운영 이미지와 별도 target이며 고정된 JWT 서명기용 OpenSSL만 추가한다.
4. `enabled: true`와 `--profile maintenance`는 운영 반영 단계에서 설정한다. 기본 profile은 꺼져
   있다. 운영자만 설정·활성화한다. 맥북에서 daemon을 실행할 필요는 없다.
5. 작은 합성 결함으로 원인 대화 → 제안 → 실제 CI → draft PR → Slack 알림을 확인한다. 실제
   구독 사용량·메모리를 측정하고, 첫 PR은 직접 검토한다. 검토한 뒤에도 배포는 별도 단계다.

명령:

```bash
quant-company maintenance --config /etc/quant-company/maintenance.json
quant-company maintenance-status
```

첫 명령은 명시된 서버 설정과 자격증명이 필요하다. 두 번째 명령은 최근 50개 case/triage의 상태·
분류·평가 방식·비교 결과·안전한 오류 코드·CI/PR 영수증을 조회한다. 원본 대화/프롬프트는 출력하지
않는다. `blocked`는 운영자가 해당 case와 GitHub 실제 상태를
확인할 대상이며, 자동으로 새 ID를 만들거나 실패한 PR을 재생성하지 않는다.

## 무엇을 관찰하고 어떻게 개선하나

최근 메시지와 오류뿐 아니라 최근 30일의 담당자별 업무/실패/재시도, 위임 방향·깊이, 동일 지시의
반복을 읽는다. 담당자 집중이나 반복 위임은 조사 단서이며 자동으로 문제라고 판정하지 않는다.
최근 7일과 그 이전 23일은 길이가 다르며 원시 건수로 성과를 비교하지 않는다. 근거는 허용된
회사 프로젝트만으로 제한하고, 스레드별 요청과 전역 동작 변경을 구별한다.

발견 건마다 `문제 → 근거 → 원인 가설 → 기대 동작 → 고정한 평가 기준`을 남긴다.

- **실행 코드:** 같은 회귀 검사가 기존 코드에서 실패하고 수정 코드에서 통과해야 한다. skip이나
  import 오류로 이를 대신하지 못한다. 기존 전체 검사도 통과해야 PR을 만든다.
- **직원 지침:** 저장된 문제 요청과 정상 요청을 한 개씩 고른 뒤, 같은 모델과 같은 문맥으로 각각
  수정 전후를 비교한다. 정상 요청의 동작을 유지하면서 문제 요청만 통과해야 한다. 비교의 도구·
  위임·메모리 등은 실제 업무로 실행하지 않는다. 수정할 수 있는 직원은 한 번에 한 명이다.
- **조직 구조·평가 불가능한 개선:** 근거와 검증 계획을 담은 설계 PR을 만든다. 역할·권한·모델을
  즉시 바꾸지 않으며, PR과 Slack 안내에 **효과 미검증**을 명시한다.

기본 모델 한도 6회/일은 그대로다. 지침 개선 한 건은 관찰 분류 1회·수정 1회·전후 비교 4회를
사용하므로 다른 업무가 있으면 여러 날에 걸쳐 진행될 수 있다. 사용자 업무가 먼저다. 재시작해도
고정된 입력과 결과로 이어가며, 실패·불확정 후 새 조건으로 자동 재시험하지 않는다.

`prompt_replay`는 두 요청의 구조화된 응답에서 상태·위임·도구·출처를 확인하는 작은 비교다.
답변 의미의 정확성, 금융 전문성, 전체 협업 성과가 좋아졌다는 증명은 아니다. 이런 효과를 주장하려면
설계 PR에서 별도 평가를 구체화해야 한다. 회사 전체의 실시간 대화를 복제해 실행하는 기능은 아니다.

## 변경 범위와 한계

- 일반 회사 런타임 모듈·문서와 역할의 mission/instructions 수정 제안을 허용한다.
- 데이터 라이브러리·연구 규약·다른 저장소·배포·인증·CI·개선 BOT 자신의 변경은 거절한다.
- 기존 테스트를 고치거나 삭제하지 않는다. Python 수정에는 case별 새 회귀 검사를 붙인다.
- 테스트 성공은 수정의 타당성이나 금융 전문성을 보장하지 않는다. 문맥이 부족하면 제안 또는 blocked로
  남긴다. 전체 서비스 구조의 자율 재작성이나 전략 실행까지 구현한 것이 아니다.
- PR에는 문제 요약·가설·재현·기대 동작·평가 기준과 비교 결과·원본 메시지 ID·base/head/digest·CI 링크가 들어간다.
  원문 대화 전체를 PR에 복제하지 않는다. 알려진 비밀 패턴은 차단하지만 임의의 개인정보나 모든
  비밀을 완벽히 탐지하는 필터라고 주장하지 않는다.
- 새로운 컨테이너의 기본 상한 128MiB는 설정값이다. 2GB 호스트에서의 실제 적합성은 profile
  활성화 인수로 측정해야 하며 현재 운영 실측과 섞지 않는다. 후보 코드의 테스트는 GitHub에서 한다.
- GitHub Actions는 계정 사용량에 합산된다. 추가 결제 한도나 요금제를 바꾸지 않는다.

## 백업과 복구

백업은 실행 중인 개선 담당도 다른 writer와 함께 정지한 뒤 DB·모델 영수증·비밀 값 없는
`maintenance.json`을 같은 구간에 저장한다. 원래 실행 중이던 프로세스만 다시 시작한다.
GitHub App 개인키는 백업에 넣지 않는다. 복구 시 별도 보관 경로에서 설정하거나 GitHub App에서
새 키를 발급하고, 기존 브랜치·CI·PR 상태를 대사한 뒤 활성화한다. 과거 DB 복원은 외부 PR을
되돌리지 않는다. 실제 운영 활성화 인수에서 이 writer 정지·복구 경로를 함께 확인한다.
