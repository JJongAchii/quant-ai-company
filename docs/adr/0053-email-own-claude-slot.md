# 0053. 메일은 자기 Claude 구독 칸에서 영상과 나란히 쓴다

- 상태: 승인 (소유자, 2026-11-20)
- 관련: [0048](0048-claude-api-credit-lane.md) API 크레딧 레인, [0051](0051-editorial-desk-on-claude-slots.md) 회사 업무 칸

## 배경

메일은 영상과 나란히 쓴다(소유자 2026-11-05). 지금까지는 메일과 영상 본편이 claude-runtime의 원래 구독 칸
(`.runtime.lock`)을 같이 썼다. 그래서 영상이 모델을 쓰는 동안 만드는 메일 요청은 API 전용(`api_only`)이었고, 영상이
그 단계에 들어서면 돌던 메일 차례를 취소했다(`yield_to_video`).

2026-11-18 15:56쯤 API 레인의 31일 사용액이 상한($190 중 $188.77)에 닿았다. 그 뒤 영상 중 메일 요청은 모두 `busy`였다.
- 사용처: Shorts 약 $118, 본편 수정·분석 약 $47, 메일 $15
- 메일이 영상이 끝날 때까지 기다렸다: 11-18 마감 18:08, 11-19 08:28·18:38 발송
- 11-20 아침은 모델 글 없이 08:40에 대체본이 나갔다(평소 07:11쯤)

Shorts는 API를 먼저 쓰므로(`API_FIRST`) 오래된 사용분이 빠져도 곧 다시 찬다. 소유자 지시(2026-11-20):
"API 한도 다쓸경우 구독으로 해서 하도록 하면되잖아."

## 결정

- 메일 차례(`newsletter_v1`)는 자기 CLI 칸 `.runtime-email.lock`을 쓴다(`claude_runner.slot`). Shorts의 칸(2026-11-18)과
  같은 방식이다. API 레인을 먼저 쓰고, 받지 못하면 그 칸에서 구독으로 돈다.
- 메일 작성기는 영상 중에도 API 전용으로 묻지 않고, 영상에 양보하지 않는다(`yield_to_video` 제거).
- 이미 API 전용으로 고정된 요청은 같은 ID·내용으로만 다시 묻는다(영수증 일치). 거절되면 5분 뒤 새 요청으로 묻는다.

## 결과

- 메일은 원래 칸(`.runtime.lock`)을 쓰지 않는다. 그 칸은 영상(본편, API가 받지 못한 영상 분석)과 직원 독립 검토(지금 꺼짐)가
  쓴다. 영상은 메일의 CLI 칸을 기다리지 않는다.
- API가 상한·꺼짐·혼잡이어도 메일은 구독으로 제시간에 쓴다. 이때 구독을 하루 2번(Opus high, 짧은 글) 더 쓴다. 구독도
  한도에 닿으면 메일은 기다리고, 대체본 시각이 되면 대체본이 나간다. 이 추가 사용은 영상과 같은 구독 한도에 들어간다.
- 남은 대기 경로(이 변경 전부터 있음): API 레인은 동시에 두 호출만 받고(`API_SLOTS`), 빈자리를 제한 없이 기다린다. 메일과
  Shorts가 두 자리를 잡고 있으면, API를 먼저 쓰는 본편 화면 수정(`video_screen_fix_v1`)이 그 호출이 끝날 때까지 기다릴 수
  있다. 메일은 이 변경 전에도 영상 중 API로 돌았으므로 이 경로는 늘지도 줄지도 않았다. API 상한에 닿아 있는 동안
  (11-18부터, 처음 빠지는 날 11-26)은 API 호출이 없어 일어나지 않는다. 따로 고친다.
- CLI가 최대 일곱 동시에 돈다(브리핑이 Codex인 동안은 여섯). 266 MB × 7 ≈ 1.9 GB로 `CLAUDE_MEMORY_LIMIT=2048m` 안이다.
- 구독은 소유자의 Claude Code와 같은 계정이다. 주간 사용률 경보(80%·95%)는 그대로 둔다.
