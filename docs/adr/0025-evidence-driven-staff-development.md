# ADR-0025: 직원별 약점 추적과 검증 가능한 지속 개선

상태: 구현 및 로컬 검증 완료, 운영 미반영. 요청 근거: 2026-09-18 대화의 “응 나는 직원의 전문성이 극대화되고
계속해서 업그레이드되면서 완전해지기를 원해”. 이 문서는 기존 qws 계약을 변경하지 않는다.

## 해결할 문제

현재 문제은행은 11개 직무의 22개 기초/중간 유형이다. 문제를 매일 푸는 것만으로 전문성이
향상되지는 않는다. 한 번의 후속 통과가 실패 피드백을 숨기고, 직원별 평가 공백이 보이지 않는다.
또한 평가 실패로 전문 절차를 수정하려 해도 `prompt_replay`는 생산 업무의 실패/정상 요청 두 건을
요구하여 합성 평가만 있는 직원의 수정·검증 경로가 끊긴다.

## 결정

- 직원별·유형별·모델/절차/suite별 증거를 기록한다. 미평가, 실패 후 재검증 중, 반복 확인을 구별한다.
  같은 구성의 서로 다른 새 과제 3회 연속 통과를 주의사항 해제 기준으로 사용한다. 이는 운영상
  재발 점검 기준이며 통계적 개선이나 전문가 자격 기준이 아니다. 실패·이의·인프라 장애는 구별한다.
- 직원 순환과 일일 호출 한도는 유지하고 직원 안에서는 미평가 영역과 취약 영역에 새 문제를 배정한다.
  한 유형의 반복이 다른 유형을 굶기지 않게 한다. 배정 이유와 입력 버전을 과제에 남긴다.
- 개선 BOT에 `staff_replay`를 연결한다. 하나의 직원 절차만 변경할 수 있고, 실제 기록된 실패가
  현재 모델·절차와 일치해야 한다. 변경 전 문제와 채점 기준을 서버에서 동결한다.
- 공개된 실패 사례, 같은 유형의 새 사례, 다른 유형의 새 대조 사례를 기존/수정 절차로 비교한다.
  새 사례와 정답은 수정 BOT에 공개하지 않는다. 요청·도구·응답을 저장하고 재시작 때 재사용한다.
  각 풀이의 도구/호출 한도와 개선 BOT의 기존 구독 제한을 적용한다. 한 비교는 최대 18회 호출이다.
- 공개 실패의 재현·수정, 새 사례 통과와 정상 경로 유지가 확인된 경우에만 수정 PR을 제시한다.
  새 사례에서 두 버전이 모두 통과했다면 우월성 미입증으로 표시한다. PR 검토와 운영 반영은 기존
  정책을 따른다. 문제·정답·채점기·비교 실행기는 개선 BOT이 수정할 수 없다.
- 직원 현황에 현재 평가 영역, 아직 검증하지 않은 전문 영역, 다음 과제의 이유, 연결된 개선 근거를
  표시한다. 전체 평균을 전문성 점수로 표시하지 않는다. 전문 지식은 기존 원문 조회와 검토 기억
  경로로 축적하고, 실제 업무 관찰은 기존 개선 BOT의 조사 경로를 계속 사용한다.

서술의 논리·근거를 평가할 다른 계열 모델은 실제 사용 가능한 제공자와 인증이 확인되어야 한다.
모델 이름만 바꾼 자기 평가를 독립 평가라고 표시하지 않는다. 별도 제공자를 연결하기 전에도
객관적 평가와 절차 수정 경로는 동작한다. 새 유료 API, 가중치 학습, 연구 워커 실행은 추가하지 않는다.

## 완료 기준

1. 같은 구성의 새 과제에서만 반복 확인되며, 과거 버전 통과·분쟁 평가·쿼터 오류가 약점을 해소하지 않는다.
2. 취약 유형 재검증과 다른 유형 탐색이 모두 예약되고 일일 예산·직원 순환·업무 우선순위가 유지된다.
3. 실제 PostgreSQL에서 평가 실패 → 개선 BOT 접수 → 동결 → 수정 → 양쪽 풀이/코드 채점 → PR 준비를
   검증한다. 도구 왕복, 중단/재시작, 이의 제기, 권한/구성 변경, 답안 유출, 위조 receipt도 검사한다.
4. 수정 BOT에 새 문제/정답이 전달되지 않으며 자체 채점 변경은 거부된다. 새 사례 우월성 미입증을 보존한다.
5. 실제 모델 확인과 fixture 시스템 검증을 구분한다. 기능 배포와 장기 전문성 향상은 별도 증거로 보고한다.

지속 평가·생산 사례·별도 평가 데이터·사람 판정에 대한 기준은
[OpenAI 공식 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)을 참고한다.
우리 직원/문제은행에 대한 개선 효과는 이 자료로 입증되지 않으며 직접 측정한다.
