# ADR-0014: BOT 행동과 협업 구조의 근거 기반 개선

상태: 구현 검토 중, 운영 비활성. 2026-09-17 KST.

사용자는 개선 대상을 BOT 동작·전문 역할·멀티에이전트 구조로 확인했고, 그 범위의 구현을
이어가는 데 동의했다. 운영 정책은 ADR-0013의 **수정·테스트·PR 자동, 운영 반영은 검토 후**다.

## 문제

초기 개선 담당은 최근 메시지 묶음에서 재현 가능한 플랫폼 결함 하나를 찾았다. 이 방식만으로는
여러 업무에 걸친 위임 집중·반복 실패를 보기 어렵고, 지침을 바꾼 후 Python 테스트가 통과해도
BOT의 실제 응답이 개선됐다고 할 수 없다. 보호된 구조 변경을 모두 버리면 중요한 개선 제안도
사용자의 검토 대상에 남지 않는다.

## 결정

기존 관찰·예산·Temporal·Git broker를 확장한다. 새 직원 서비스나 별도 상시 모델은 추가하지 않는다.

### 1. 장기 기록과 근거

- 허용 소유자의 회사 DB를 동일한 repeatable-read snapshot으로 읽는다. 최근 30일을 이전 23일과
  최근 7일로 구분해 담당자별 업무/turn 상태, 시도·재시도 수, 위임 방향·깊이와 같은 지시의 반복을
  집계한다. 원시 건수와 구간 길이를 제공하며 서로 다른 구간의 건수를 성과 비교로 쓰지 않는다.
- 이것은 생성 시점별 현재 상태다. 성공률·만족도·응답 정확도나 순수 모델 추론 시간을 추정하지
  않는다. 반복된 동일 지시도 합당한 업무일 수 있다. 집계만으로 원인을 확정하지 않는다.
- 최근 메시지 최대 24개와 이미 기록된 완료 turn 요청 최대 6개를 추가 근거로 제공한다. 요청
  하나는 25KB 이하이며 큰 요청·알려진 비밀 패턴·권한 밖 기록은 제외한다. 표본 한계를 함께
  남긴다. 원본 프롬프트는 DB의 평가 입력으로 보존하고 triage에는 요청 식별자·업무 요약만 준다.
- `platform_defect`, `bot_behavior`, `collaboration`, `organization` 분류, 원인 가설, 증거 ID,
  기대 동작, 수정 전에 고정한 평가 방식을 남긴다. 리뷰 snapshot·평가 기준·입력의 digest를
  저장하고 후속 단계에서 대조한다. 한 스레드의 요구를 전역 개선 권한으로 해석하지 않는다.

### 2. 개선 유형별 검증

| 방식 | 대상 | PR 전에 필요한 근거 |
|---|---|---|
| `regression` | 허용된 런타임 코드 결함 | 동일한 새 회귀 검사가 parent에서 assertion 실패, candidate에서 통과. 수집 오류·skip·검사 제거는 거절. 기존 전체 검사도 통과 |
| `prompt_replay` | 직원 한 명의 mission/instructions | 아래의 고정된 문제 사례와 정상 사례를 같은 모델로 전후 비교하고 CI 통과 |
| `documentation` | 기존 일반 문서의 수정 | 문서 CI와 사람 검토. 실행 코드·지침을 이 방식으로 검사하거나 행동 향상을 주장하지 않음 |
| `design_only` | 조직·역할/권한·모델 배치·전문성 등 현재 자동 평가 범위를 넘는 변경 | 관찰·가설·기대 동작·향후 성공 기준을 담은 설계 문서와 문서 CI. 행동 개선은 미검증으로 표시 |

역할 지침의 Python 검사 통과를 행동 개선 근거로 사용하지 않는다. 코드와 지침을 한 번에 바꾸는
패치는 현재 자동 평가 대상이 아니다. 구조 변경은 사람이 검토할 `docs/improvements/<case>.md`
PR로 남긴다. 이 문서를 머지해도 직원이나 권한이 바뀌지 않는다.

### 3. 저장된 요청의 전후 비교

1. triage에서 서로 다른 저장 요청 두 개를 선택한다. 하나는 고칠 문제, 하나는 보존할 정상 동작이다.
   두 입력 모두 해당 finding에 인용돼야 한다. 성공 기준은 patch 생성 전에 저장한다.
2. Git base의 역할과 저장 요청의 모델·역할 지침·권한·version이 일치해야 한다. 직원 한 명만
   바꾸며, base의 역할 블록만 candidate 지침으로 대체한다. 나머지 시스템 문구·업무·대화·출처
   snapshot은 바꾸지 않는다. 임의로 만든 대화를 실제 이력으로 쓰지 않는다.
3. 각 요청에 대해 base/candidate를 각각 한 번 호출한다. 회사 업무 실행기에 결과를 commit하지
   않으므로 응답 속 도구·위임·메모리·Slack 발신은 실행하지 않는다. 평가 하나의 모델 request ID와
   응답은 DB에 고정한다. 재시작은 같은 요청을 재사용하고 한 tick에 최대 한 응답만 진행한다.
4. LLM의 자기 평가 대신 구조화된 응답을 코드로 판정한다. 완료/대기 상태, 위임 대상, 도구 종류,
   산출물 유무·출처 ID를 검사한다. 권한 밖 동작·출처나 새 예약 업무도 감지한다.
5. base에서 문제 사례가 실패하고 정상 사례가 통과해야 한다. candidate에서는 둘 다 통과해야 한다.
   정상 사례 악화는 `failed`, 문제가 재현되지 않으면 `inconclusive`로 종결하며 자동 재튜닝하지 않는다.

이 검증은 **두 사례의 한 번씩의 생성 결과**다. 생성의 확률성·전체 응답 품질·금융 지식의 옳고
그름을 검증하지 않는다. 통과가 통계적 향상이나 실전 성과를 뜻하지 않으며 PR에 한계를 명시한다.
사람이 기준의 타당성과 변경 내용을 검토한다. 다중 직원의 실제 대화 전체를 재실행하는 기능도
아니다. 그런 구조 변경은 설계 제안과 이후 승인된 별도 인수로 남긴다.

### 4. 예산·발행·운영

관찰 10분, 단계 진행 5분, 사용자 업무 우선, 회사 공통 한도 안에서 개선 모델 호출 하루 최대 6회를
유지한다. 일반 지침 개선 한 건은 triage 1 + patch 1 + 비교 4로 6회다. 다른 업무/개선 건과 경쟁하면
여러 날에 걸칠 수 있다. 호출 수는 수정 건수나 토큰 한도가 아니다. 유료 API fallback은 추가하지 않는다.

PR에 원인 가설·평가 기준 digest·기록 snapshot digest·비교 결과·한계와 정확한 Git/CI 근거를
붙인다. 설계 제안의 Slack 알림에는 효과 미검증을 명시한다. 자신의 알림은 새 관찰에서 제외한다.
자동 merge/배포·외부 레포 변경·개선 담당 자신의 변경 권한은 추가하지 않는다.

## 검증과 남은 인수

실제 PostgreSQL의 소유자 필터·기간 집계·입력 고정·예산 우선순위·재시작 복구와 scripted model을
사용한 통과/악화/불확정 분기를 검증한다. 회귀 비교는 임시 Git 저장소와 실제 pytest subprocess로
수정 전후를 실행한다. 기존 Temporal history replay도 유지한다.

운영 데이터로 발견한 문제의 실제 구독 응답 비교, GitHub App 발행, Slack 왕복, 서버 추가 메모리
실측은 운영 연결 인수에 남아 있다. 이 구현 검사를 실제 LLM 행동 향상이나 운영 활성화로 보고하지 않는다.
