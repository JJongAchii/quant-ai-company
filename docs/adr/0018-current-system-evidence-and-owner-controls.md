# ADR-0018: 현재 구현 근거에 따른 진단과 소유자 운영 명령

2026-09-17 · **Accepted** · 사용자 지시 “진행해 그리고 회사 공통 100회 한도는 없애지 그래?”에 따른 구현.
배포·실제 인수 결과는 별도 영수증을 근거로 판정한다.

## 문제와 확인한 사실

사용자는 같은 Slack 스레드에서 개선BOT 한도 해제와 다른 스레드의 구조적 한계 진단을 요청했다.
총괄은 보관 기록 19건을 읽었으나 운영 설정을 바꾸지 못했고, 이미 보완한 문제와 남은 기능을 섞어
개선 대상으로 보고했다. 현재 구현과 해결 여부를 진단 입력에 연결하는 경로가 부족하다.

[조사 기록](../project/CURRENT-SYSTEM-DIAGNOSIS.json)의 확인 범위:

- GitHub `main`과 서버 배포 모두 `ae7517c5fbe79db92c1c19396a60711ecac120e1`이다.
- 기존 대기 진단은 `2842ab33c4f43c25058fdd3073854ce070b37db9`의 저장소 snapshot을 보존 중이다.
  첫 모델 호출도 예약되지 않은 상태에서 최신 코드와 다른 기준으로 대기하고 있다.
- `GitHub.snapshot()`은 커밋·파일 목록을 조회하지만 triage 모델에는 주로 수정 가능한 경로만
  전달한다. 관련 코드 본문은 문제를 고른 뒤 patch 단계에서 읽는다.
- `GitHub.read_files()`도 수정 가능 여부를 요구한다. 진단에 필요한 인증·설정·개선 담당 내부를
  읽는 권한과 수정 권한이 함께 제한되어 있다.
- 이력 조회는 사람 요청·결과 중심이다. 회사 전체의 승인·PR 병합·배포·검증 영수증을 연결한
  현재 상태를 제공하지 않는다. PR #3의 문서 반영 완료 영수증은 별도 테이블에 이미 있다.
- `report()`는 과거 finding을 그대로 반환한다. 사실관계가 틀렸거나 이후 해결된 가설을 현재
  진단에서 제외하는 정정 상태가 없다. `problem_key`의 단일 case 재사용도 재발과 옛 결과를 혼동할 수 있다.
- 개선 전용 한도는 6회/일이며 설정 스키마는 1~12만 허용한다. 총괄의 한도 변경 도구는 없다.
  한도 변경 요청이 같은 개선 모델 큐에 들어가므로 그 큐의 한도에 다시 막힌다.

## 결정과 구현

기존 GitHub App, PostgreSQL, Temporal, Slack 수신·발신 경로를 사용한다.
진단 순서를 **요청 확인 → 현재 구현·운영 근거 조회 → 과거 사건과 대조 → 미해결 항목 진단**으로 바꾼다.

### 1. 총괄과 개선 담당이 같은 현재 상태를 읽는다

PostgreSQL에 버전이 있는 시스템 상태 snapshot을 보관하고 두 소비자가 같은 조회 함수를 사용한다.
GitHub 자료는 기존 maintenance 프로세스가, 실제 배포 사실은 기존 호스트 배포 실행기가 발행한다.
총괄 모델에는 공개 가능한 사실과 출처만 전달한다.

| 근거 | 필수 정보 |
|---|---|
| 저장소 | repo·branch·exact commit·조회 시각, 관련 파일의 blob SHA와 경로 |
| 코드 이해 | 고정 커밋의 관련 구현·테스트·ADR·변경 diff, 읽은 범위와 생략 여부 |
| PR·CI | 사람이 올린 PR과 BOT PR 모두, 대상 head·병합 커밋·검사 결과·조회 시각 |
| 실제 운영 | 배포 커밋·로드된 역할 및 공개 설정 digest·활성 기능·호스트 확인 시각 |
| 동작 검증 | 기능 ID·실행 경로·대상 코드와 설정·결과·실행 시각·검증 한계 |

상태는 최소한 `미구현 / 저장소에 구현 / 운영 배포 / 활성화 / 동작 검증 / 확인 불가`를 구분한다.
PR 제목·문서·일반 CI 통과만으로 실제 운영 문제의 해결을 확정하지 않는다. 문서 변경은 배포가
필요 없을 수 있고, 코드가 배포돼도 기능 설정이 비활성일 수 있다. 근거가 없는 항목은 확인 불가다.

대표 예: Slack 승인 연결은 관련 구현·검사와 실제 PR #3 병합·알림 영수증을 함께 표시한다.
이 문서 사례의 성공을 모든 코드 후보의 배포·실패 복구까지 검증했다는 의미로 확장하지 않는다.

### 2. 코드 읽기를 진단 앞단으로 옮기고 읽기·쓰기 권한을 분리한다

- 정확한 커밋에 고정한 저장소 검색·파일 읽기를 총괄과 개선 진단에 제공한다. 회사 저장소의
  허용된 소스·테스트·ADR·배포 템플릿을 제한된 크기로 읽으며 결과에 commit·path·blob을 붙인다.
- 진단할 때는 현재 수정 금지인 모듈도 읽을 수 있어야 한다. 기존 수정 허용 목록과 사람의
  운영 반영 승인은 유지한다. 모델에 GitHub 개인키·운영 secret·셸 실행을 제공하지 않는다.
- 전체 저장소를 매번 프롬프트에 넣지 않는다. 요청과 연결된 자료를 골라 읽고, 범위가 부족하면
  추가 읽기 또는 확인 불가로 남긴다. 저장소 내용도 모델 지침으로 실행하지 않는다.
- 모델의 finding은 과거 사례와 현재 코드·운영 근거를 함께 인용해야 한다. 서비스는 참조한
  커밋·파일·영수증·권한이 실제 snapshot에 속하는지 검사한다. 의미 해석 자체가 자동 보장되지는 않는다.

### 3. 과거 사건·원인 가설·해결 상태를 따로 보존한다

- 원본 대화와 실패 영수증은 보존한다. 별도의 정정·해결 기록에 이유·근거·대상 버전·시각을 추가한다.
- case의 작업 단계와 사실 판정을 분리한다. 예: `blocked`는 작업 중단이며 결함이 사실이라는
  증거가 아니다. 사실 판정은 `미확인 / 현재 재현 / 해결 근거 있음 / 가설 기각`으로 표시한다.
- “당시 제공된 이력을 무시했다”는 기존 finding은 저장된 원 입력과 대조한 정정 기록을 연결한다.
  조회·답변에서는 과거의 기각된 가설로 표시하고, 현재 확인된 결함 목록에서 제외한다.
- 완료된 PR·배포·검증 사실을 관련 요청과 case에 연결한다. 배포 사실만으로 자동 해결하지 않고
  그 문제의 성공 기준을 충족한 근거가 있는지 확인한다.
- 같은 문제가 실제로 재발하면 새 발생 기록을 이전 case와 연결한다. 반복 수집은 중복 제거하되,
  이전에 성공했다는 이유로 새 실패를 덮지 않는다. 운영자 시험·재처리는 실제 사람 요청과 구분한다.

### 4. 대기 후 재개할 때 근거의 유효성을 확인한다

- 진단·수정 제안·게시 전에 저장소, 배포, 설정의 현재 digest를 확인한다.
- 아직 모델 호출을 예약하지 않았다면 최신 snapshot으로 새 진단 revision을 만들고 이전 자료를
  보존한다. 이미 예약·응답·평가가 있는 요청은 입력을 덮어쓰지 않고 변경된 근거를 새 revision에 묶는다.
- 관련 근거가 바뀌면 기존 제안을 그대로 게시하지 않고 재대조 대상으로 둔다. 기존 replay 입력은
  당시 직원이 본 자료로 보존하며 현재 코드의 상태와 혼합하지 않는다.
- GitHub 또는 서버 확인이 실패하거나 오래됐으면 마지막 확인 시각과 불확실성을 표시한다.
  읽기 실패를 기능 부재로 해석하거나, 무관한 매 커밋마다 모델 진단을 새로 시작하지 않는다.

### 5. 소유자 운영 명령을 개선 모델 큐에서 분리한다

한도 변경은 서명된 Slack 이벤트의 실제 소유자·채널·명령을 확인하는 서비스 처리기로 보낸다.
총괄은 문맥을 설명할 수 있지만 자기 권한이나 호출량을 승인할 수 없다.

- 변경 가능한 항목·값을 정해 둔 typed command를 사용한다. 명확한 소유자 명령은 중복 없이
  처리하고, 대상이나 값이 모호할 때만 구체화한다. 임의 셸·파일 변경 명령으로 전달하지 않는다.
  질문·인용문·BOT 메시지는 소유자의 적용 명령으로 취급하지 않는다.
- `요청됨 → 적용됨 / 거절됨 / 실패` 상태와 요청 원문·이벤트 ID·변경 전후 값·설정 revision을 기록한다.
  성공 응답은 실제 적용값을 다시 읽은 뒤 발신한다. 동시 변경과 재시작에도 같은 효과가 반복되지 않아야 한다.
- 사용자 후속 지시에 따라 **개선BOT 전용 6회와 회사 공통 100회 일일 제한을 모두 제거**한다.
  기본 설정 `0`과 DB 정책의 해제 값은 일일 quota 없음을 뜻하며 사용량 계측은 보존한다.
  모델 동시 실행 1개·업무당 8턴·위임 깊이 3·프로젝트 40업무·사용자 업무 우선·실제 구독 한도는 유지한다.
  유료 API fallback이나 추가 결제를 활성화하지 않는다.
- 유효 정책은 버전이 있는 DB 기록으로 읽고 호출 예약과 함께 검사한다. 설정 적용과 상태 조회는
  개선 모델 호출을 필요로 하지 않아, 개선 호출 한도가 찬 상태에서도 수행할 수 있어야 한다.
- 한도 변경과 진단이 한 요청에 있으면 두 결과를 각각 추적한다. 총괄의 답변 완료를 전체 요청의
  이행 완료로 표시하지 않고, 미처리 항목·담당자·대기 사유를 계속 보여준다.

## 구현 순서와 변경 위치

| 순서 | 구현 범위 | 주요 위치 |
|---|---|---|
| 1 | 읽기 전용 저장소 근거, 현재 배포·설정 snapshot, 총괄·진단 공통 조회 | maintenance/github.py, observation.py, requests.py, company.py, 호스트 배포 영수증 |
| 2 | 기각·해결 상태 연결, 최신 기준 재대조와 재발 구분 | maintenance/schema.sql, store.py, runner.py, applications.py |
| 3 | 소유자 한도 명령과 독립적인 적용·결과 보고 | slack.py, config.py, maintenance/policy.py·store.py, 관련 schema |
| 4 | 기존 요청 재진단과 실제 Slack 인수 | 원래 case·요청을 보존한 운영 재처리 |

이는 현재 서비스의 첫 수정 범위다. 웹 자료 수집·데이터 전수 검사·연구 워커 연결은 별도 기능이다.
아침 브리핑·요청형 시장 분석 BOT은 기존 로드맵의 추후 구현 상태를 유지한다.

## 성공 기준

1. 과거 “모델 설정을 모른다”·“반영해를 실행 못 한다”는 요청과 현재 구현·검증을 함께 주면,
   근거 범위에서 해결된 내용을 구분하고 같은 기능의 신규 개발을 제안하지 않는다.
2. PR 병합만 된 경우, 배포됐지만 기능이 꺼진 경우, 동작 검증까지 있는 경우를 각각 구분한다.
3. 기각된 가설은 원본을 보존하되 현재 확정 사실로 인용되지 않는다. 재발은 새 근거로 추적된다.
4. 진단 대기 중 코드·설정이 바뀌면 이전 커밋 기준 제안이 그대로 게시되지 않는다. 이미 보존한
   모델 요청과 평가 영수증의 digest도 바뀌지 않는다.
5. 개선 호출 6/6 상태에서도 허용된 소유자 한도 명령을 처리하고 실제 적용값을 보고한다.
   중복 이벤트·무권한 사용자·설정 경쟁은 별도로 검증한다.
6. 한도 해제와 진단의 복합 요청에서 둘의 처리 상태가 보이며, 접수만 된 진단을 완료로 표시하지 않는다.
7. PostgreSQL·변경된 처리 경로·기존 회귀 검사를 통과한 뒤, 제한된 실제 Slack 인수로 현재 사실
   조회와 운영 명령의 왕복을 확인한다. 모델 진단은 고정 사례의 의미 정확성도 검토한다.

검증 결과는 대상 commit·공개 설정 digest·실행 시각·실제/모의 경계와 함께 남긴다.
이 문서만으로 운영 인수나 모델 판단 정확성을 주장하지 않는다. 구현은 읽기 전용 archive의 blob 검증,
허용된 파일·줄 검색, 최근 15개 PR·CI, 역할·설정·이미지 커밋, append-only 정정·검증 기록을 사용한다.
모든 코드의 의미를 자동 판정하지 않으며 신규 실패의 인과성은 고정 기준과 검증을 요구한다.
GitHub 확인 장애에는 진단을 대기시키고 마지막 상태를 확인 불가로 표시한다.
선별된 코드 발췌만으로 판단할 수 없으면 추가 조회 또는 미확인으로 남긴다.
