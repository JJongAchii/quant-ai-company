# ADR-0017: 총괄의 이력 조회와 개선 진단 요청 연결

2026-09-17 · Accepted · 사용자 요청: 진단 스레드에서 확인한 연결 공백 수리 진행.

## 문제와 근거

총괄에게 과거 요청을 개선BOT으로 진단하라고 했지만, 총괄은 등록 자료 검색만 수행했다.
당시 저장된 모델 입력에는 새 요청 한 건과 합성 인수 자료만 있었다. 자동 관찰기는 나중에
이 스레드를 읽었으나 자신이 본 이력을 총괄도 봤다고 가정해 지침 수정을 제안했다.
또한 지침 변경에 Python 테스트를 추가하는 제안이 만들어져 평가 방식 검사에서 차단됐다.
요청자가 개선 서비스의 대기·진단·실패를 같은 스레드에서 조회할 경로도 없었다.

## 결정

새 직원·컨테이너·유료 API 없이 기존 총괄과 maintenance 큐를 연결한다.

1. 총괄에 `company_history`, `maintenance_review`, `maintenance_status` 도구를 추가한다.
   이력 조회는 같은 소유자의 현재 허용 Slack 채널과 DM, 최근 30일의 기록에 한정한다.
   최대 20개 요청과 결과를 반환하고 표본·문구 길이 제한과 비밀 패턴 생략을 표시한다.
   결과는 현재 프로젝트 전용 source로 등록한다. 금융 출처나 직원의 당시 입력으로 해석하지 않는다.
2. `maintenance_review {}`는 현재 사람 요청의 실제 task ID로 멱등 접수한다. 모델이 소유자,
   대상 프로젝트, 승인 또는 작업 원문을 만들어 넣지 않는다. 소유자당 분류 전 요청 3건을 상한으로 둔다.
3. `maintenance_jobs`의 review → triage → 기존 case 연결을 사용한다. 사용자의 명시 요청은
   자동 관찰보다 먼저 처리한다. 수집 시 소유자 범위의 이력을 한 트랜잭션에서 고정한다.
4. 유지보수 프로세스가 자격증명 없는 공개 운영 상태와 heartbeat를 DB에 기록한다.
   총괄은 현재 스레드의 실제 접수·case·PR·실패 상태를 조회한다. heartbeat 지연은 표시하고
   접수와 완료를 구별한다. GitHub App key나 maintenance 설정 파일을 총괄에 노출하지 않는다.
   Slack 수신기뿐 아니라 실제 도구를 실행하는 worker와 maintenance에도 동일한 공개 사용자·채널
   허용 목록을 전달한다. 운영 인수에서 이 전달 누락으로 정상 요청이 차단된 것을 확인했으며,
   Compose를 해석한 환경으로 실제 도구를 호출하는 회귀 검사를 추가했다. Slack 토큰은 전달하지 않는다.
5. 정상 종료·후보·PR뿐 아니라 호출 한도·일시 대기·검증 차단도 기존 outbox로 보고한다.
   상태별 알림 ID를 고정해 재시작·중복 tick에도 반복 발신하지 않는다. 같은 case의 PR을 다른
   진단 스레드에 연결해도 실제 PR 알림이 전달된 뒤에만 기존 정확한 커밋 승인 경로를 사용할 수 있다.
6. 관찰자 문맥과 직원 문맥을 구분한다. 기록된 원 요청에서 직원이 받은 메시지·출처·도구를
   추출해 진단에 제공한다. 큰 문맥은 생략 사실을 표시한다. 존재하지 않은 출처·도구·위임을
   요구하는 replay 기준은 patch 모델 호출 전에 거절한다. 지침 변경에는 Python 테스트 파일을
   요구하지 않고 고정된 두 요청의 전후 평가를 적용한다. 도구·이력 연결 부족은 설계 문제로 다룬다.

## 유지하는 경계

- 기존 구독과 개선 모델 호출 6회/일, 회사 전체 100회/일을 유지한다. 한도는 DB 날짜 기준이다.
  요청·상태 조회 자체는 추가 개선 모델 호출이 없고, 실제 진단은 기존 한도에서 실행한다.
- 역할·도구 권한 변경은 이번 사람이 승인한 구현이다. 개선BOT 자신의 권한 변경은 자동 허용하지 않는다.
- PR까지 자동, 운영 반영은 검토 후 정확한 후보 승인이라는 기존 정책을 유지한다.
- 과거의 잘못된 진단·blocked 영수증은 고치거나 성공으로 덮어쓰지 않는다.
- 원인 가설과 한정된 replay 통과가 금융 전문성·일반적 자율 수리 능력을 증명하지는 않는다.

## 검증

실제 PostgreSQL에서 사람 업무 → 도구 → 영속 진단 → 같은 스레드 outbox, 중복·권한·출처,
한도 대기·검증 실패·revision 변경, 기존 PR 연결 후 승인 경로를 검사한다.
이번 장애처럼 관찰자만 본 후속 이력을 원 직원 문맥으로 오인하는 입력과 불가능한 출처 기준을
회귀 사례로 고정한다. 모델·GitHub·Slack의 테스트 경계와 실제 서버 인수는 운영 영수증에서 구분한다.
